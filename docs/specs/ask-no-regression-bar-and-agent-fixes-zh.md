## 1. 先把验收标准落成可检验的形式

### 1.1 业主给这次升级的标准

> **Ask 模式的新实现不能比原来的差，最好是大于等于现有系统。Agent 模式是新的。**

**请注意这句话允许什么、不允许什么：**

- ✅ **允许**把 Ask 换成一条新实现（现在的 Fast Ask）。换路本身**不是问题**。
- ✅ 允许它更快、更省、结构更清楚。
- ❌ **不允许在任何一个可观察的维度上比老 Ask 弱**，除非有对应的补偿证据。

### 1.2 问题的准确形状

**"不能比原来差"这句话，现在没有任何一条测试在守。**

你们有 1668 个单元测试，它们测的是**管道**：返回值形状、权限隔离、脱敏。
**没有一条断言"新 Ask 的能力面 ≥ 老 Ask"。**

🔴 **这就是这次退化能够一路走到业主面前的原因。**
不是谁写错了代码 —— 是**这条要求从来没有被翻译成机器能检查的东西**。

所以本文第一优先的不是改代码，是**先把这把尺子做出来**。否则下一次升级还会这样。

### 1.3 三条基准线（建议做成 CI 断言，不是一次性检查）

#### 基准线 A —— 答案质量：通过集合只许增不许减

`evals/` 的 39 条 case，**两条路各跑一遍**：

- legacy Ask（`investigation_mode` 不传）
- 现在的 Ask（`investigation_mode=fast`）

**判据**：`fast` 的通过集合必须 **⊇** legacy 的通过集合。
**少一条就是退化**，每一条差异都要逐条给出理由（不是给出分数）。

🔴 **先决条件**：本地 copilot-api 的 **HTTP 502** 必须先修好。
你们已经指出来了 —— 19/21 个失败是它，0.0–0.1 秒就红，**模型压根没被调到**。
**在 502 修好之前，任何一次评测都不能作为"没有退化"的证据。**

⚠️ 另外你们发现盒子上的 `evals/last_run.json` **只有 4/4**（不是外网以为的 19/20）。
所以**这一轮要顺便把真正的基线建起来**：legacy 那一遍的结果就是基线，存成一份**不会被覆盖**的文件。

#### 基准线 B —— 能力面：老 Ask 有的，新 Ask 不能没有

| # | 老 Ask 的行为（外网 `webapp/agent.py`） | 断言 |
| --- | --- | --- |
| 1 | **每一轮**都把工具全集交给模型（`:164`） | 新 Ask 每一轮可见 schema 数 = 全集（`incident_investigate` 走 contract 的除外） |
| 2 | 一个问题最多 **8 轮**工具（`:161`，`MAX_TOOL_ITERS`） | 可用工具轮数 ≥ 老 Ask |
| 3 | 工具抛异常 → 异常文本作为 `role:"tool"` 回喂（`:220-223` ＋ `:249-253`） | 失败文本进入下一轮 messages **且下一轮模型手上仍有工具** |
| 4 | 终结事件字段：`answer` / `tool_trace` / `usage` / `citations` / `views` / `subagent_steps` / `context` | **只许增，不许减** |

**任何一条收窄，都必须在同一次提交里给出"为什么这不算变差"的证据。**
没有证据就不算收窄合理 —— 这条规矩比具体某个数字更重要。

#### 基准线 C —— 首字延迟

Ask 的 provider delta **立刻**发 `token`（`webapp/agent.py:837-842`）。
**新 Ask 的首 token 时间不能显著晚于老 Ask。**

（Agent 不受这条约束：它在全部执行 ＋ synthesis ＋ gate 之后才发 answer token
（`webapp/agent_loop.py:3480-3529`），**首字天然晚，这是设计不是缺陷** ——
但前端必须把中间的 progress event 当作可见进度，否则用户看到的就是白屏。）

## 2. 已确认的一条退化 —— Fast Ask 第二轮起没有工具

### 2.1 证据（内网自己在 SEND-BACK 里写的）

> 「Ask 当前普通工具路径会把失败 `result` 作为 `role:"tool"` 加回 messages
> （`webapp/agent.py:1133-1144`）；但 **Fast Ask 明确只给首个 tool round 暴露 schema，
> 下一轮不再允许工具**（`webapp/agent.py:821-836`）。所以失败文本虽然会被模型看见，
> **模型仍不能在该 Fast Ask turn 内重调工具自修**。」

对照基准线 B：

| | 老 Ask | Fast Ask |
| --- | --- | --- |
| 可用工具的轮数 | 最多 **8** | 实际 **1** |
| 工具失败后能不能重试 | **能** | **不能** |

**这是一次明确的能力收窄，而且没有补偿证据。**

### 2.2 为什么这条特别要紧

🔴 **模型看得见自己失败了，手上却没有工具，还被要求给出答案。**

这比"错误没有回喂"更糟。截图一那个答案的形状 ——
「抱歉，当前文档查询参数不兼容」＋ 一段通用常识 ＋「未验证」＋ `no citations to verify`
—— **是这个约束下唯一可能的产物**。它不是模型偷懒，是被逼的。

### 2.3 不改的后果

**任何一次工具失败 = 这一轮整个报废。**

而工具失败在这套系统里是**常态**，不是异常：参数格式对不上、对端不可达
（截图二那次就是 Portal `connection_refused`）、数据集没绑上……
**每一次都会退化成"道歉 ＋ 通用常识 ＋ 未验证"。**

用户看到的是"**它突然什么都不知道了**"，而系统其实只是被拿走了第二次机会。

### 2.4 改完的效果

第一次参数写错 → 模型看到"哪个字段错了、期望什么" → 第二轮改对 → 拿到数据 → 带引用作答。
用户什么都不用做，多花一两秒。**这正是老 Ask 的行为。**

### 2.5 怎么改（三条，都很小）

#### (1) 判据从"第几轮"改成"上一轮有没有失败的工具调用"

- 上一轮**全部成功** → **维持现状**，撤掉 schema。**"fast" 的本意一点不动。**
- 上一轮**有失败** → 下一轮**继续带 schema**。

🔴 **这是改一个判断条件，不是改架构。不要把 Fast Ask 改成 Agent。**

#### (2) 给"买回"一个明确上限

一个配置项（名字你们定），**默认 2 轮**。
用完还失败 → 正常收尾，**并且在答案里写明"试了 N 次仍失败"**，
而不是静默退回通用常识。

#### (3) 🔴 回喂的文本必须说清「哪个字段 / 期望什么 / 实际拿到什么」

不是把异常对象 `str()` 一下。
**模型改不对参数最常见的原因，是错误信息没说期望值。**
这正是外网第四轮踩过的坑：`2026-07-30 03:15 HKT` 原样传被真机拒绝，
实际要 `alert_time` ＋ `timezone` **分开传** ——
如果错误信息只说"格式错误"，模型永远猜不到。

### 2.6 验收

1. 端到端：构造一个必然参数失败的工具调用 → **第二轮模型带着 schema 重试 → 成功**；
2. 断言：上一轮**全部成功**时，schema 仍按现状撤掉（**证明没有把 fast 改成 deep**）；
3. 断言：买回轮数用完后，最终答案里出现"试了 N 次仍失败"，而不是静默的通用常识；
4. 断言：回喂文本包含**字段名和期望格式**，不是裸异常字符串。

### 2.7 临时止血（可选，一句话就能确认）

在 2.5 落地之前，**把前端 "Ask Mode" 按钮发的 `investigation_mode` 改成不传**（走 legacy Ask），
就能立刻回到基准线 —— 因为"原来的"按定义就是那条线。

**要先确认两件事：**

1. 前端那个按钮**现在**发的是 `fast` 还是不传？
2. legacy 那条路**现在还跑得起来吗**？

- 跑得起来 → 这是零代码风险的临时手段，业主今天就能用回一个正常的 Ask；
- 跑不起来 → **直接说"不可达"**，那 2.5 就是唯一路径，不用再找开关。

🔴 **这只是临时手段，不是最终形态。** 最终形态是 2.5 —— Fast Ask 留下来、但不再有这条收窄。

## 3. Agent 侧 —— 三条真缺陷

Agent 是新模式，不受"不能比原来差"约束。但下面三条是**实打实的缺陷**，
而且直接对应业主说的"**一 block 就停 / 不知道为什么停 / trace 老半天**"。

### 3.1 `invalid_proposal` 和 `internal_contract_conflict` 必须分开

#### 问题

> 内网原话：「当前源码确认 `invalid_proposal` 和 `internal_contract_conflict` **都映射到**
> `internal_contract_error`（`webapp/agent_loop.py:495-507`）；Incident Contract 在这种 decision 下
> **直接记录 gap/blocked runtime，而不把可修的工具错误回喂给 executor**
> （`webapp/agent_loop.py:671-836`）。」

这两个东西的性质**正好相反**：

| decision | 是什么 | 谁能修 | 正确的下一步 |
| --- | --- | --- | --- |
| `invalid_proposal` | 模型把参数写错了 | **模型自己** | 回喂 → 重试 |
| `internal_contract_conflict` | 我们两个组件对不上 | **模型和用户都不能** | 标成我们的缺陷、落 telemetry、**别去问用户** |

**好消息：分类你们已经做对了一半。** 那唯一一条 `internal_contract_conflict` 样本带的是
`user_action_required=false`、`resumable=true`、`primary_cause=internal_contract_conflict`
—— **判得很准**。缺的只是把 `invalid_proposal` 从这个桶里拿出来。

#### 不改的后果

- 模型自己三秒能改好的参数错误，被记成系统缺陷 → **白白丢掉一次本来能成功的调查**；
- 反过来，真正的系统缺陷如果被当成"可重试"，就会**反复重试一个必然失败的东西**，把 90 秒耗光。

**两个方向都是错的，而它们现在共用一条路。**

#### 🔴 安全论证（这是唯一可能被挡下来的地方，先写在这里）

**把 `invalid_proposal` 回喂给模型，不扩大任何权限。**

它发生在 `action_within_harness_decision()` **之前** —— 是对一个 *proposal* 的校验，
**此刻没有任何真实 MCP / 生产动作发生**，ceiling、approval、budget 三道闸门**一条都没有动**。
模型改完参数**还要再走一遍完整的 preflight ＋ harness**。

**"不回喂"换来的不是安全，只是一次白白浪费的往返。**

#### ⚠️ 一个必须顺手查的洞

你们的样本 N=12 里 **`invalid_proposal = 0`**，但业主说"**参数校验错误经常出现**"。
两者不可能都对。两种可能：

- **(a)** 它真的很少，业主看到的"参数校验错误"是**别的东西**
  —— 比如截图一那句「文档查询参数不兼容」，那是**工具层**的错，不是 harness 的 decision；
- **(b)** 它发生了，但**没被记成这个值** —— 在到达 harness 之前就失败了。

🔴 **如果是 (b)，那分类表本身有个洞：有一类参数错误根本没进入这七个枚举。**
请顺手确认是 (a) 还是 (b) —— **这决定了本节要不要多修一处。**

#### 验收

1. 三个用例（参数写错 / 内部不一致 / 缺时区）→ **三条不同的下一步**；
2. `invalid_proposal` 那条**产生第二次工具调用**；
3. `internal_contract_conflict` 那条**不出现在给用户的提问里**，
   但 telemetry 里能定位到**具体是哪个字段**对不上；
4. `policy_denied` 的措辞里出现"限制"，**不出现"查不到 / 无数据"**。

### 3.2 一份账 —— 以及「不知道」不许渲染成「没有发生」

#### 问题

> 内网原话：「同一 assistant turn 关联的 safe debug trace **没有** incident-contract/runtime/MCP 类型 span；
> 它只保留了 execution/model/terminal 类 span。与此同时，run-step serializer **又没有保留**
> `contract_triggered`、`runtime_entered` 和 MCP counter 的具体值。
> **结论：两块 UI 确实没有从同一份完整版本读取；现有保留数据也不足以还原右侧三个布尔值的来源。**」

而 session 侧的记录是**清楚的**：`run_steps` 里有 `incident_contract_dispatch`、
`incident_runtime_entry`、`incident_mcp_summary` ＋ 5 条 `subagent_step`，
**harness decision = `approved`**。

> 内网原话：「session-side 记录支持"**Contract 已触发且实际发生过 Incident/MCP 路径**"，
> 不是"未触发 Contract"。」

🔴🔴 **所以截图二左边是对的，右边是错的。屏幕上那句「Harness 未批准进入 Incident runtime」是假的。**
真实情况是 harness **批准了**（`approved`），运行进去了，然后 **Portal MCP 连接被拒**。

**这个 bug 的准确形状不是"数字算错了"，是"把『不知道』渲染成了『没有发生』"** ——
面板拿不到值，于是显示 `否 / 0`，而不是显示"这一段没有记录"。

#### 不改的后果

**每次出问题都被指向错误的那扇门。** 截图二让业主去查权限和审批，
而真相是 **Portal 服务连接被拒绝** —— 一个网络/对端问题。

**更糟的是第二层**：一个对什么情况都说同一句「Harness 未批准」的面板，**等于没有面板**。
真的哪天是 harness 拒绝，也分不出来了。

#### 改完的效果

停下来的时候，用户在**答案位置**就看到三句话，不用点任何东西、不用开 debug：

```
为什么停在这里：  Portal 服务连接被拒绝，重试 2 次后放弃
谁能解开：        不是你，也不是我们的策略 —— 是 Portal 那边或网络
解开之后会怎样：  能补上短信投递记录，把这次的结论闭合
```

#### 怎么改（五条）

1. 🔴 **面板只读一份账，而且必须是执行时写的那份**，不是事后重建的。哪一份由你们定。
2. 🔴🔴 **「没有记录」≠「否 / 0」。** 布尔值和计数器取不到时显示 `—`。
   你们右侧那格 `Zero Call Reason` **已经会显示 `—` 了** —— **把这个做法推广到全部字段**。
   **这一条是本节最重要的。**
3. **run-step serializer 要保 `contract_triggered` / `runtime_entered` / MCP counter 的具体值**
   （这条是你们自己指出来它没保的）。
4. **加 terminal `blocked`。** `webapp/server.py:1521-1525` 现在只认
   `done | cancelled | budget_exhausted`，于是一个 `run.status=paused` 的 run **外层发的是 `done`**。
   🔴 这条 `harness-borrowings-implement-zh.md` §B.4-2 已经定过：
   「**pause 理由必须显式，绝不许伪装成 completed**」—— 现在它有了第二个实例。
   **一个"在等"的 run 和一个"做完了"的 run，在记录里必须一眼分开。**
5. **三段渲染**：`who_can_close_it` / `resolution_owner` **已经在 gap/closure 记录里了**，
   只差把它提到 terminal 顶层、并在**答案位置**渲染出来。

#### 验收

1. 断言：**取不到值的布尔/计数器渲染成 `—`，不是 `否` / `0`**；
2. 端到端：一次 MCP 连接失败的 run，面板显示的原因指向**对端**，**不出现"Harness 未批准"**；
3. 断言：`run.status=paused` 的 run，terminal event **不是** `done`；
4. 断言：三类停止的 `who_can_close` **三条各不相同**（用户 / 我们 / 配置拥有者）。

### 3.3 时区 disclosure —— 只差一条断言

**这一条你们做对了，而且比外网上一轮要求的更完整**：

**只差最后一格**：`notice_required=true` 的时候，

"这个时区是按默认策略补的，不是从告警原文里读到的"。

**为什么值得单独立一条**：一个"记了但没显示"的 notice，和没记是一样的 —— **用户看不到**。
这和外网上一轮抓的 **"0% ＝ 双厂商备用，不是关掉了"** 是同一个形状：
系统内部知道，用户不知道，于是用户按错的理解做决定。

#### 验收

一条断言：`notice_required=true` → **最终 answer text 中包含时区来源说明**。
（`honesty-no-timezone-must-not-describe-logs` 本次 **PASS 9/9**，
说明"缺时区不许往下走"这条已经守住了；这条补的是"补了默认要说出来"。）

## 4. 不做什么

- ❌ **不要松 `answer_gate`。**
  三个症状是**一条链**：工具调不到 → 没有证据 → 没有可挂的引用 → 答案空泛。
  **闸门是在替上游的"证据饥饿"背锅，它一次都没做错。**
  松了不是"答案变好"，是**从"空泛但诚实"变成"自信但错误"** ——
  上一轮 `857de51` 已经真机证明过（两个模型各写一个时区，闸门拦得完全正确）。
- ❌ **不要因为那 19 条 502 去改任何 prompt 或闸门。** 你们这个判断是对的。
- ❌ **不要把 Fast Ask 改成 Agent。** §2.5 的判据是"上一轮有没有失败"，不是取消 fast。
- ❌ **不要现在动 `tool_subset` 或 lane 份额。** 见 §5。
- ❌ **不做旧版的 F0**（`runtime_context` 那条已被你们的源码证伪，见 §6）。
