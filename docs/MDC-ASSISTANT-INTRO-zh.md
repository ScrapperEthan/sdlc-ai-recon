# MDC Assistant 是什么 —— 写给第一次听说它的人

> 本文面向**完全没接触过这个系统的人**，不需要任何背景知识，也不需要会写代码。
> 读完你应该能：跟别人解释清楚这东西是干嘛的、它现在能干什么、不能干什么、下一步往哪走。
>
> 状态截至 **2026-08-08**。

---

## 一、60 秒读懂

**一句话**：MDC Assistant 是一个「懂整个 MDC 通知系统」的问答助手 —— 你用中文问一句话，它自己去翻代码、翻配置、翻业务路由表、必要时翻生产日志，然后给你一个**每句话都能点开看出处**的答案。

**它把四层原本互不相通的东西接在了一起：**

| 层 | 里面是什么 | 回答什么问题 |
|---|---|---|
| ① 代码层 | 460 个 Java 仓库的源码、依赖关系、跨仓库调用链 | 改这个类会连累谁？谁调用了它？ |
| ② 消息层 | 服务之间的异步布线：谁往哪个队列发、谁在收 | 这条消息从哪来、到哪去？ |
| ③ 业务层 | 用例、渠道规则、厂商路由表（数据库快照 + 可直连 UAT 只读库） | 这条通知走短信还是邮件？最后交给哪家厂商？出事要通知谁？ |
| ④ **运行层** | **生产日志、监控指标、投递记录**（通过三台 MCP 服务器实时查） | **它昨晚 3 点为什么挂了？这条通知到底发出去没有？** |

**为什么这四层接起来才有价值**：单看任何一层都答不了真正的问题。代码告诉你"这个仓库依赖那个仓库"，但答不了"所以哪个业务受影响"；业务表告诉你"这个用例走短信"，但答不了"短信服务的代码是哪个仓库、它昨晚报了什么错"。**把四层串起来的那条线，就是这个项目真正的资产。**

> ⭐ **第 ④ 层是最值得单独讲的一层，我们把它叫 AIOps 2.0。**
> 前三层是"我们自己建的索引"，第 ④ 层是**实时连到生产系统去取真相**。
> 而且关键不在于"能连上"——连日志谁都能连——**关键在于它知道该查什么**：
> 查哪个应用、哪些关键词、哪个时间窗，全都是**从前三层推导出来的**。
> 这一段展开在 **§五**，是本文最长的一章。

**愿景**：从「能回答」走到「能动手」—— 完整的 AI 软件开发流程是
`读懂代码 → 写需求文档 → 出设计 → 生成代码 → 编译测试 → 出 diff → 人工评审`。
我们目前把**第一段（读懂）做得很深**，中间几段跑通了一条窄窄的样板路径，**人工评审这一环永远保留**。

**现在实现到哪：**

| 能力 | 状态 | 说明 |
|---|---|---|
| 跨仓库问答 / 影响分析 | 🟢 已上线 | 核心能力，也是最深的一块 |
| 业务全链路（用例 → 渠道 → 厂商 → 出口） | 🟢 已上线 | 链路通到底了，但厂商结论受源数据限制（见 §七） |
| 事故影响面（告警 → 谁受影响） | 🟢 已上线 | 零生产访问，真实数据识别率 93.2% |
| **AIOps 2.0：连生产查根因** | 🟡 **引擎全通，等一张对照表** | 三台 MCP 全部真机验证、工具名零偏差；卡在**只有 1 个应用有名字映射**（见 §5.9） |
| 新模块脚手架 / 改一个已有服务 | 🟡 样板路径 | 真实跑通过：生成改动 → 编译 → 测试通过 → 出 diff |
| 自动部署 | ⚪ 有意不做 | 银行环境，部署永远由人来点 |

## 二、为什么需要它（背景）

MDC 是一整套「通知投递系统」—— 银行要给客户发短信、邮件、App 推送、WhatsApp、信件，都从这里走。

它被拆成了 **460 个 Java 仓库**。这带来一个很现实的问题：

> **没有任何一个人知道全貌。**

于是三类高频问题，今天都只能靠"去找那个待了五年的人"：

1. **「我改这个公共模型，会连累谁？」** —— 依赖关系散在 460 个 `pom.xml` 里，没人能手工数完。
2. **「这条通知到底怎么走到客户手机上的？」** —— 一半答案在代码里，一半在数据库配置表里，两边对不上。
3. **「凌晨这条告警是谁的事？要不要叫业务方起床？」** —— 告警只说了某个服务 CPU 高，说不出这影响哪些业务。

**这三个问题的答案，分别散落在四个互不相通的地方，而且没有任何一个现成工具能同时看到这四层。** 这就是 MDC Assistant 存在的理由。

## 三、它是怎么工作的（这段决定你怎么信任它）

### 1. 模型不"背"代码，它是个「会用工具的人」

常见误解是"把 460 个仓库喂给大模型"。做不到，也不该做。

实际的机制是：**你问一句话 → 助手判断该查什么 → 调用几个检索工具去查预先建好的索引 → 拿到真实结果后再回答你。**

这带来一个重要后果：**它答不上来的时候会说答不上来，而不是编一个。** 因为答案不是"想"出来的，是"查"出来的 —— 查不到就是查不到。

### 2. 每句话都带出处

答案里的每个结论后面都跟着一个可点击的引用，点开直接看到那一行源码或那一行配置。**你不需要相信助手，你只需要点开看。**

> 📷 **截图位**：一个带引用的回答 + 点开引用后的源码面板

### 3. 结论分档，不把"猜的"和"查到的"混在一起

这是整个项目最较真的一点。举个真实例子 —— 问"这个用例的短信最后交给哪家厂商发"，答案会分四档：

| 档位 | 意思 | 助手会怎么说 |
|---|---|---|
| **权威** | 权威路由表匹配上了，厂商名也经业主确认 | 「走 X 厂商」 |
| **权威但名字未签认** | 表里确实写了厂商，但那个写法业主还没确认等于哪一家 | 「权威表记录的是 `HTCL`」—— **原文照抄，绝不翻译** |
| **线索** | 路由配置的名字里像是有厂商名 | 「有线索指向 X，但这只是线索」 |
| **渠道级上界** | 只知道这个渠道总共就那几家 | 「**最多**是这几家之一」—— 不说"它走 X" |

**为什么这么啰嗦**：因为把"最多这几家"说成"就是这家"，在事故里会让人去联系错的厂商。**目前只有约 1/4 的用例能拿到权威厂商**，所以第四档是常态，不是缺陷。

### 4. 全程只读

助手**永不修改 MDC 的产品代码**，也不会在生产上做任何写操作。事故排查路径上一个写操作都没有。

## A 组：我要改东西 —— 会连累谁？

### A1 · 依赖影响面

**一句话**：查一个仓库的"爆炸半径" —— 谁依赖它、它依赖谁、改动会波及多远。

**你会怎么问**：
> 「改 `xxx-api-common` 会影响哪些仓库？」
> 「这个仓库能不能动？风险多大？」

**它回你什么**：直接依赖者 + 传递依赖者的完整清单，可以顺手**把依赖关系图画在回答里**，不用另开页面。

⭐ **新增（本轮）—— 渠道分层卡片**：光说"376 个下游"是**正确但没用**的。所以现在还会告诉你：**这个仓库自己管哪些渠道**（实线卡），以及**改了它会连累哪些渠道**（虚线卡，默认折叠）。每张卡都带证据条数，点进去能跳到源码那一行。

真实数据：**322 个仓库有渠道证据，其中 127 个同时命中 2 个以上渠道** —— 旧版本一直在把这 127 个各压成一个渠道，也就是**近四成仓库的渠道被少报了**。

**它不做什么**：依赖关系来自 Maven 配置，是"编译期"的关系。**A 依赖 B ≠ 运行时真的会调到 B**。要看真实调用关系，用 A2。

> 📷 **截图位**：渠道卡片（多渠道仓库 + hub 仓库两种）
> 💬 **示例位**：一次完整的影响面问答

---

### A2 · 跨仓库真实调用链

**一句话**：谁真的调用了这个类/这个方法 —— 精确到源码行，跨仓库。

**你会怎么问**：
> 「谁调用了 `IngressService`？跨仓库的调用链是什么？」

**它回你什么**：真实的调用者清单（不是文本搜索的近似匹配），每个都带 `仓库/文件:行号`，并且能把调用链画成图。

**它不做什么**：这一层靠一个叫 CodeGraph 的代码索引，它**不覆盖全部 460 个仓库**（还差 66 个）。覆盖不到的时候助手会**如实降级说"这里查不到"**，而不是偷偷退回成关键词搜索给你一个像模像样的假答案。

---

### A3 · 消息谁产谁消

**一句话**：这个队列/主题，谁在往里发、谁在收。

**你会怎么问**：
> 「谁在消费 `otx_bat_letter`？生产者是谁？」
> 「这个仓库收发哪些消息？」

**它回你什么**：生产者、消费者、或某个仓库涉及的全部消息边，逐条带证据出处。

**它不做什么**：这是**异步布线**，不是实时流量。它告诉你"配置上谁连着谁"，不告诉你"现在每秒多少条"。

---

### A4 · 仓库目录与全景

**一句话**：MDC 到底有哪些仓库？哪些是对外 API、哪些是定时任务、哪些是公共库？

**你会怎么问**：
> 「MDC 一共有哪些仓库？给我完整清单和一张全景图。」
> 「有哪些 tracking 相关的仓库？」

**它回你什么**：按名字、角色（api / job / core / lib）、渠道、系统筛选后的仓库清单，可以顺手渲染一张**全景图**。

**一个必须说清的口径**：MDC 的业务足迹 = **45 个业主确认的仓库**，另有 **2 个图上相邻的候选**待确认。所以正确说法是"45 个已确认 + 2 个待确认"，**永远不要说"完整"**。

> 📷 **截图位**：仓库全景图

---

### A5 · 核心仓库盘点

**一句话**：哪些仓库最不能出问题 —— **分维度打分，不给一个总榜**。

**你会怎么问**：
> 「最核心、最不能出问题的 10 个仓库是哪些？」

**它回你什么**：三个独立维度各自的排名 —— 依赖中心度、消息中心度、业务影响面 —— 外加一个"等权合并视图"。

**为什么不给一个总榜**（这点值得单独讲，是典型的"看起来对但其实错"）：

> 按依赖数排序，公共库一定第一（所有人都依赖它，但它不承载任何消息）；
> 而一个投递任务承载了全行所有短信，却没有任何仓库依赖它。
> **一个总榜会悄悄替听众选了一种"核心"的定义。**

**它不做什么**：**生产流量、故障历史、测试覆盖率这三个维度算不了**，而且每次回答都会**主动说出来算不了、卡在谁那里**。所以这是"今天能测量的东西的 Top 10"，不是"真实的 Top 10"。

---

### A6 · 源码搜索与读原文

**一句话**：兜底工具 —— 直接在只读代码镜像里搜文本、读带行号的源码。

**你会怎么问**：
> 「找到支付状态是在哪里映射的，并引用源码行。」

**它不做什么**：**这是兜底，不是首选**。问调用关系优先用 A2（精确），问依赖优先用 A1。文本搜索会命中一堆同名但无关的代码。

## B 组：我要搞懂业务 —— 一条通知怎么走到客户手上？

### B1 · 一个用例讲到出口 ⭐ 旗舰功能

**一句话**：给一个业务用例编号，从头讲到尾 —— 一直讲到客户手机上收到什么。

**你会怎么问**：
> 「K3002 的完整配置与渠道是什么？把全链路讲到出口。」

**它回你什么**，一条完整的链：

```
业务用例 → 渠道规则（发短信还是邮件？先发哪个？）
        → 权威路由表（厂商 / SLA / 投递等级）
        → 消息主题 → 投递任务 → 出站 API
        → 厂商 → SMSC / APNs / 邮件网关 / 打印出口
```

外加：治理信息（owner 是谁）、同意/opt-in 前置检查、配置一致性检查结果。

**三个细节值得单独说**：

- **发送顺序是有语义的**。规则表达式里 `>` 表示"左边失败了才发右边"、`&` 表示"一起发"、`|` 表示"二选一"。这意味着：**前一级正常的时候，后面那些渠道根本没在发** —— 影响面不能把它们全算成活流量。
- **0% 的厂商不是"关掉了"，是备用**。这是最值钱的一次纠正。配置里 `流量=0%` 的那一行，是**故意配的第二家厂商**，也就是主力挂掉时接管的那一家。真实数据：**897 个渠道是"正在发 + 背后有一个 0% 备用"**。修正之前，问"主力厂商挂了谁接管"，这 897 个渠道**一个都答不出来**。
- **SLA 数字的单位是毫秒**（由代码证据推定，业主尚未正式签认），所以助手会说"60000 毫秒（1 分钟），单位由代码推定"。

**它不做什么**：厂商结论**必须**按 §三.3 的四档如实标注。**它不会把"最多这几家"说成"就是这家"。**

> 📷 **截图位**：全链路回答 + 架构图高亮到出口
> 💬 **示例位**：一个真实用例的完整问答

---

### B2 · 用例目录搜索

**一句话**：在约 2800 条业务用例里按条件找一批。

**你会怎么问**：
> 「找 HK 的 SMS 用例」「列出所有 PEGA 的批量用例」

**它回你什么**：按国家、渠道、上游系统、业务分类等筛选后的清单，**服务端分页**（不会一口气把整张表倒给你）。

**跟 B1 的分工**：B1 是"查一个已知编号的全部细节"，B2 是"按条件找一批"。

---

### B3 · 用例 ↔ 消息主题路由

**一句话**：这个用例走哪个主题；反过来，这个主题上还挂着哪些用例。

**你会怎么问**：
> 「M2050 走哪个 topic？」
> 「这个 topic 一改，还有哪些用例会受影响？」

**它不做什么**：这份路由快照来自 **dev/SCT 环境，不是生产**。所以"这里没有" **≠** "生产没有"，助手每次都会声明这一点。

---

### B4 · 上游系统影响面

**一句话**：某个上游业务系统出问题 / 要改动，影响哪些用例、哪些渠道，**要通知谁**。

**你会怎么问**：
> 「PEGA 出问题会影响哪些用例和渠道？改动要通知谁？」

**它回你什么**：该系统喂了哪些用例、覆盖漏斗（配置到哪一步了）、渠道链、上下游仓库，以及**分层的联系人**：真实业务 owner > 成本治理签核人 > 配置维护人。

**"要通知谁"这一条是它最直接的业务价值** —— 这个问题今天靠人肉记忆，而记忆会退休。

**它不做什么**：覆盖漏斗描述的是**配置完成到哪个阶段**，不等于"消息真的送达了客户"。

---

### B5 · 架构图高亮

**一句话**：把整条受影响的链路**直接画在回答里**并高亮，你不用去点任何节点。

**你会怎么问**：
> 「短信渠道挂了会影响什么？」
> 「PEGA 接进来的位置在架构图上是哪里？」

**它回你什么**：一张 MDC 投递管线的架构图，受影响的那条路径从上游一路高亮到厂商出口。**文字解释照给**，图只是帮你一眼看懂。

> 📷 **截图位**：渠道故障高亮 / 用例全链路高亮

---

### B6 · 配置数据体检

**一句话**：把全量业务配置扫一遍，列出互相矛盾的地方，按严重程度排序。

**你会怎么问**：
> 「现在的用例配置有哪些数据质量问题？」

**它回你什么**：孤儿配置行、启用了却没有渠道规则的用例、可能引发空指针的字段、以及**规则表达式和优先级互相打架**的那些用例。

**它不做什么**：这些是**多个数据源之间的分歧标记，不是已确认的生产故障** —— 助手每次都会这么说。

---

### B7 · 直连 UAT 只读库

**一句话**：对 UAT 数据库跑一次**受控的只读查询**，拿到当下的真实数据。

**怎么用**：**助手不能写 SQL，也没有任何途径要求写一条** —— 它只能从内网声明好的查询名单里挑一个来跑。

**它不做什么**：
- **UAT 不是生产**。数据可能是复制的、脱敏的或者合成的，助手绝不会把 UAT 的一行说成生产事实。
- 查询失败 **≠** "没有这条记录"。"没接线"、"被拒绝"和"查不到"是三件不同的事。

## C 组：界面上其他你会看到的东西

这些不是"检索功能"，但每天都会用到。

| 功能 | 一句话 |
|---|---|
| **会话管理** | 每次对话自动存档、自动起标题，可以按标题或对话内容搜索历史。不同浏览器之间互相隔离。 |
| **每人接自己的大模型** | 没有共享额度这回事 —— 每个人把自己的模型端点注册进来，你的对话走你自己的模型。 |
| **MCP 控制台** | 点顶栏的状态标签会打开一个面板：有哪几台外部服务器、各自有哪些操作、分别是干嘛的，还能"实时核对"我们声明的工具名和对方实际提供的对不对得上。 |
| **引用点开看源码** | 回答里的每个 `仓库/文件:行号` 都能点，右侧直接开出那段源码。 |
| **日志原文追溯**（默认关闭） | 内测期专用：可以点开看未脱敏的原始日志，用来核对调查员**有没有编造**。🔴 正式使用前必须关闭，开启期间界面会一直挂红色提示条。 |
| **用量统计 / 反馈** | 每轮问答花了多少 token、调用了哪些工具；答得不好可以当场标记并留言。 |
| **答案质量回归测试** | 22 条固定评测用例，每条都绑定一个具体的历史教训。改完东西跑一遍，防止"修好的毛病又犯回去"。 |

## 五、AIOps 2.0：连上生产，回答「为什么挂」⭐

> 这一章是整套系统里**唯一能碰到运行时真相**的部分，也是最值得单独拿出去讲的一条线。
> 前面四章讲的都是"我们自己建的索引"，这一章讲的是**实时连到生产系统去取答案**。

---

### 5.1 先说清楚「1.0」长什么样

事故这条线上，团队里已经有一套在用的 AIOps。它的做法是：针对最高频的那几族告警，**用规则判断"要不要重发"**，输出一个动作。这件事它做得不错，我们**不打算重建它**。

但它答不了三个问题：

1. 这条告警**影响哪些业务用例、哪些渠道、要不要叫业务方起床**
2. 它**为什么**挂 —— 而不是"要不要重发"
3. 结论的**出处在哪**，我凭什么信

**我们做的就是它答不了的这一层。**

---

### 5.2 2.0 差在哪 —— 一张表看完

| | AIOps 1.0（规则式） | **MDC Assistant 2.0** |
|---|---|---|
| **入口** | 固定的几族告警 | **任意告警原文粘进来就行** |
| **查什么** | 规则里写死的关键词 | **从代码图和业务图推导出来**：那个仓库真实会抛的异常类、它产/消的主题、它服务的渠道 |
| **查哪里** | 单一数据源 | **三台 MCP，三条互不拖累的分支**（日志 / 指标 / 投递记录） |
| **输出** | 一个动作（重发 / 不重发） | **谁受影响 + 为什么挂 + 每条带出处** |
| **业务影响** | 没有 | 涉及哪些用例、哪些渠道、该通知谁 |
| **查不到的时候** | 返回空 | **明确区分"没去查"和"查了没发现"** |

**一句话总结**：**1.0 回答"这条告警怎么处置"，2.0 回答"这条告警是怎么回事"。**

---

### 5.3 三台 MCP 分别是什么（**它不只是查日志**）

这是最容易被简化掉的一点。实际接了三台，各自回答完全不同的问题：

| 服务器 | 里面是什么 | 回答什么问题 | 你得先知道什么 |
|---|---|---|---|
| **日志平台** | 各应用的异常日志、链路日志；**两个生产日志源，内容不一样** | 「它报了什么错？」 | 应用名 **+ 时间窗（必须带时区）** |
| **CloudWatch** | 告警定义 + 监控指标曲线 | 「挂之前的曲线是什么形状？」 | 告警名 + 时间窗 |
| **投递记录（Portal）** | 单条消息的投递结果 | 「这条通知到底发出去没有？」 | **只要一个 tracking id** —— 不需要仓库、不需要告警名、不需要时间窗 |

⭐ **一个必须知道的事实**：**最大的那一族告警里，既没有仓库名，也没有告警名。** 日志和 CloudWatch 都拿它没办法，**只有投递记录这条路能查**。所以把 MCP 简单理解成"查日志"，会正好漏掉最重要的那一条。

三台服务器**全部真机验证过，工具名零偏差**（日志平台 6 个操作 / CloudWatch 30 个 / 投递记录 55 个）。

> 📷 **截图位**：MCP 控制台面板（三台服务器 + 各自的操作目录 + "实时核对"）

---

### 5.4 一条告警从头走到尾长什么样

```
       你把告警原文粘进来
              │
   ┌──────────┴──────────┐
   │                     │
【谁受影响】          【为什么挂】
零生产访问            连生产查证据
   │                     │
识别仓库 93.2%      ┌────┼────┐
   │                │    │    │
涉及哪些主题      日志  指标  投递记录
   │                └────┼────┘
哪些业务用例             │
   │                 脱敏证据包
哪些渠道 / 通知谁        │
   └──────────┬──────────┘
              │
     一个带出处的完整回答
```

**左右两半是故意分开的两个功能**，因为它们的风险完全不同：左边一个生产字节都不读，右边真的连上去。**任何时候都不能把左边的推断说成右边的证据。**

---

### 5.5 C1 · 告警影响面（零生产访问）

**一句话**：把一条告警原文粘进来，告诉你**谁受影响**。全程**不碰生产任何东西**。

**你会怎么问**：
> 直接把告警原文粘进去：`prodECS_xxx_service_CPUUtilizationMINOR[80percent]`
> 「这个告警影响了谁？涉及哪些业务用例和渠道？要通知哪些 owner？」

**它回你什么**：识别出的仓库（**并说明是怎么认出来的**：告警里直接写了 = 确认；靠映射推的 = 候选）、涉及的消息主题、挂在这些主题上的业务用例、渠道、以及该通知谁。

真实数据识别率：**466/500 = 93.2%**，抽查 0 认错。没认出来的那些，**是仓库名压根不在名册里**，不是解析出错。

**它不做什么**（这三条会写在每次回答里）：
1. **这一路读不到任何生产数据** —— 所以它给的是**影响面，永远不是根因**。
2. **"算不出来"和"没有影响"是两回事**。算不出精确的业务影响时，它会明说算不出，并退回给一个"最多 N 个"的上界 —— **而不是返回一个会被读成"没有业务影响"的 0**。
3. 认不出仓库时会**直接问你是哪个服务，绝不猜**。

> 💬 **示例位**：一条真实告警的影响面回答

---

### 5.6 C2 · 根因调查 —— 真的去读生产

**一句话**：连上三台 MCP，读生产日志、监控指标和投递记录，回答"它到底为什么挂"。

**你会怎么问**：
> 「看一下生产日志，这条告警的日志说明了什么？」
> 追问：「时间窗再宽一点」「换个关键词再查」「只看某个日志源」「多查几个关键词」

#### 它怎么工作（四条，这是 2.0 的核心）

**① 我们出查询计划，对方只负责执行。**
关键词**不是"搜 ERROR"**，而是**从我们前四层索引推出来的**：那个仓库真实会抛的异常类、它产/消的主题、它服务的渠道。

> **这一条就是 1.0 和 2.0 的分水岭。** 通用 AIOps 工具能连上日志，但它不知道"这个服务在这种故障下应该报什么异常" —— 那个知识在代码里，而我们恰好把代码读透了。**接日志是接线工作，推出该查什么才是能力。**

**② 三条分支同时跑，互不拖累。**
投递记录、指标、日志各查各的，**任何一条成功都不掩盖另一条的沉默** —— 一条查到了，不代表另外两条也查了，回答里会分开说。

**③ 单独开一个隔离的"调查员"去读。**
原始日志**只存在于调查员进程的内存里**，经过三层脱敏后才返回一个结构化证据包（命中行数、异常类、最多 5 行脱敏摘录）。**原始日志永远不进模型上下文，也不进聊天记录。**

**④ 每一步都在界面上流式显示。**
查了哪个应用、哪个日志源、哪些关键词、命中多少行、调用了哪台 MCP、耗时多久 —— 并且**区分"本地就拒绝了（根本没发请求）"和"服务器没响应"**。你能看着它一步步查，而不是等一个黑盒结果。

> 📷 **截图位**：调查员流式面板（每一步的 MCP 徽章 + 耗时）
> 💬 **示例位**：一次完整的根因调查（含追问深挖）

#### 它不做什么（每条都是踩坑换来的）

- **时间窗是硬门槛，不是提醒。** 缺日期或缺时区，它**一次查询都不会发**，并明确告诉你缺的是哪一半。原因值得讲给别人听：**CloudWatch 记 UTC、日志平台默认香港时间、服务器是 GMT —— 同一个"3:15"可能是相隔 8 小时的三个时刻。**
- **应用名不猜。** 查不到映射时会**明确拒绝并说明原因**。
- **"没去查"和"查了没发现"严格区分**，前者一定会说出来。
- **指标只给形状，不给数值。** 曲线的原始数据点在进程内算完就丢，只留下"在涨/在跌、波动大不大、有没有过线"这类分类结论 —— 所以你问"平均值多少"它给不出来，这是设计如此。
- **一行日志本身不是根因。** 它只说日志显示了什么，不替你下推断。

---

### 5.7 安全边界（合规上要能一句话说清）

**原始生产日志只存在于调查员进程的内存中**，经过三层防护才返回：取数时脱敏 → 出口再扫一遍并**记账** → 硬性的条数和长度上限。手机号、邮箱、账号、证件号、tracking id 全部替换成**带稳定指纹的标记**（同一个值在 40 行里仍然看得出是同一个，但值本身不出现）。

**落盘的聊天记录里不可能出现原始日志。** 这一条有专门的测试：往日志里种入个人信息，断言返回包里任何角落都找不到。

> ⚠️ **一个内测期例外**：为了让运维能核对"调查员有没有编造"，有一个**默认关闭**的开关，打开后可以点开看未脱敏原文。即使打开，**模型仍然只收到脱敏结果**，原文不进模型上下文也不进聊天记录，只是单独存一个文件供人点开。🔴 正式使用前必须关闭，开启期间界面一直挂红色提示条。

---

### 5.8 为什么这件事比"能连上"难得多

把 MCP 接通只是第一天的工作。真正的工程量在**这些失败模式**上 —— 列出来是因为它们有一个共同点：

> 🔴 **失败长得像成功。** 它们全都返回一个空的、看起来很正常的结果，而**空会被读成"没问题"**。

| 踩过的坑 | 后果 | 怎么修的 |
|---|---|---|
| 关键词没命中时，服务端**静默返回文件尾部** | 我们标成"命中 N 行" → **拿无关的生产日志给出一个自信的错误根因** | **本地逐行复核关键词是否真的出现**，不依赖对方 |
| MCP 调用有四种结果（传输失败 / 跑了但报错 / 成功但零命中 / 成功有内容），不分流 | **把错误正文当成日志证据**，调用失败被报告成"查到了日志" | 四路分流，报错的绝不进证据 |
| 日志源名字里一个字母认错（`l` 看成 `1`） | 一半的日志源全被服务器拒绝 → **静默丢掉一半覆盖** | 名字一律由内网填配置，查询前逐个向服务器核验 |
| 应用**在列表里** ≠ 允许读它 | 一批无关仓库能靠命名规则混进查询范围 | 显式的映射范围，范围外**零调用**直接拒绝 |

**这四条的修法有一个共同点：全都是"本地自己再验一遍"，不依赖对方的返回是不是诚实。** 这是把 MCP 接进生产排查最难、也最值钱的部分。

---

### 5.9 现在卡在哪（**只差一张表**）

引擎侧的活儿做完了，三台服务器全通、真机验证过。但是：

> 🔴 **目前只有 1 个应用配好了"服务名 ↔ 日志平台应用名"的对照。**

也就是说，一个已经验证可用的事故调查引擎，**现在只覆盖一个应用**。

实测过自动匹配的效果：直接同名率 **0%**，按命名规则推能唯一命中约 **36%** —— 剩下的 64% 助手会**明确拒绝查询并说明原因**（拿猜的名字去查会返回空，而空会被读成"没问题"，这正是最危险的失败方式）。

**解法很小**：一份两列的对照表，**不用全量 460 个，先给告警最多的 20–30 个就够解锁演示**。内网约半天工作量。**这是整个项目当前性价比最高的一项。**

---

## 六、它明确不做的四件事

这四条是**设计如此，不是缺口**。对外介绍时要主动讲，否则会被当成"功能不全"。

1. **永不修改 MDC 的产品代码。** 发现问题只出报告和方案，不出 PR。所以"接入一家新厂商"这种需求，它的终点是一份**可评审的改动方案**，不是一次提交。
2. **不自动部署。** 银行环境里部署由治理流程管着，永远由人来点。未来最多做成"辅助人类走部署检查清单"。
3. **不猜。** 查不到就说查不到；分不清就分档说；名字没签认就原文照抄不翻译。
4. **不做字段级数据流分析。** 现在能回答"这里可能记录了完整手机号"，**不能证明"它从未流到别处"**。后者需要另一套分析能力，列在下一阶段。

---

## 七、现在的瓶颈：**引擎在等数据，不是数据在等引擎**

这是当前最重要的一句判断，也是汇报时最该说清的一句：

> **今天卡住的不是助手的能力，是同环境的数据和运行时事实。**

| 卡在什么上 | 挡住了什么 | 谁能解开 |
|---|---|---|
| 🔴 **服务 ↔ 日志平台应用名 的对照表** | 事故根因调查 —— **目前只有 1 个应用有映射**，引擎再好也只覆盖一个应用 | 内网运维，约半天 |
| 🔴 **UAT 数据库的只读账号授权** | 直连实时查询（代码已建好，没连过真库） | DB owner |
| 🟡 **五张业务表同一时刻导出一次** | 现在几张表导出时间不同，**跨表连接其实是跨时间连接** —— 连不上可能只是导出时刻不同 | DBA，一张工单 |
| 🟡 **厂商显示名的签认** | 只差业主一句"是"，就能从"表里记着某个代号"升级到"走某某厂商" | 业务 owner |

**最高性价比的一项是第一条**：一份 20–30 行的对照表（不用全量 460 个），就能把一个已经验证过的事故调查引擎从"覆盖 1 个应用"解锁到"覆盖热点应用"。

---

## 八、路线图

**已经完成的（🟢）**
读懂代码 → 影响面 → 业务全链路 → 事故影响面。这一段做得很深，也是别人短期内追不上的部分。

**正在推进的（🟡）**
- 事故根因：引擎已通、等数据
- 代码生成：目前只支持一种样板改动（加一个接口），要扩展到消息监听、数据访问、配置等更多改动类型

**下一阶段（⚪）**
- **契约索引**：统一扫出对外发布的 API 契约、消息契约 —— 补上"改公共模型会影响外部谁"的最后一圈
- **数据库模型图**：把落库那一段和回执那一段接进全链路
- **异常语义图**：能回答"超时之后到底会不会重复发送"这类问题
- **字段级数据流分析**：能回答"手机号一共流经了哪些地方"
- **产品化**：目前是单机本地运行、没有登录、没有审计日志 —— 演示够用，给团队用还不够
