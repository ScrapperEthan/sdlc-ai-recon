## 1. 🔴 内网 §2.4 揭示了一个隐藏死锁 —— 这是本轮最重要的新发现

内网 §2.4 列了四条本地代码事实。**它们分开看都不严重，合起来是一个死锁。**

```
1. 模型 tool-call 的 JSON 参数解析失败 → 参数被替换为 {}
2. 工具拿着 {} 执行 → 报错"缺少参数 X"
3. 模型收到"缺少参数 X" → 它去补参数 X …… 但它的 JSON 还是坏的
4. 再次解析失败 → 又变成 {} → canonical_signature 相同
5. 同参去重命中 → 第二次调用被直接跳过
6. 模型永远不知道"我的 JSON 坏了"
```

🔴🔴 **模型被告知的错因，和真实错因是两件事；而它想再试一次的路，被去重堵死了。**

这和这个项目上一轮抓到的那个病**完全同形**：
截图二里屏幕说「Harness 未批准」、真相是 `connection_refused` ——
**都是把一个错误归因成另一个错误，然后把人（或模型）指向错误的那扇门。**

**必须在 implementation 里单独处理，两条：**

1. **在解析失败的那一刻就打上 `bad_call_syntax`，不许降级成"缺少参数"。**
   参数替换为 `{}` 是可以的（它保护了后面的代码），
   **但"为什么是 `{}`"这个事实必须被保留下来，而不是被丢掉。**
2. 🔴 **解析失败的调用不许生成可去重的 `canonical_signature`。**
   要么不生成签名，要么给一个每次都不同的签名。
   **否则第二次尝试会被去重挡死 —— 模型连试的机会都没有。**

**验收**：构造一次坏 JSON 的 tool-call →
断言模型收到的 `failure_class` 是 `bad_call_syntax`（**不是** `bad_arguments`）→
断言第二次调用**没有**被去重挡掉。

## 2. 错误分类契约 —— 本轮的核心设计

内网 §2.4 说得很清楚：现在没有统一 code，`error` 多是自由文本，
**"回传字段/期望/实际"这个验收要求，没法从现有任意 error 文本拼出来。**

所以这一节给的是**要建的那张表**，不是"从现有文本里提取"。

### 2.1 设计原则（只有一句）

> 🔴 **只有"模型改了下一次输出就可能成功"的失败，才值得再花一轮。**

其余的重试，只是把同一个失败重演一遍，还多烧一次模型调用。

### 2.2 `failure_class` —— 封闭枚举，由确定性代码在 dispatch 边界赋值

**模型不参与赋值，也永远看不到自由文本的原始 error。**

| `failure_class` | 什么时候 | 模型可修？ | 消耗买回额度 | 回喂给模型的话（形状） |
| --- | --- | --- | --- | --- |
| `bad_call_syntax` | tool-call 的 JSON 解析失败 | ✅ | ✅ | "上一次调用的参数不是合法 JSON。请重新发出这次调用。" **不给字段建议**（因为我们根本没解析出字段） |
| `bad_arguments` | 缺参 / 类型错 / 枚举外 / 未知 id / 未知 repo | ✅ | ✅ | `field` ＋ `expected` ＋ `actual_type` |
| `empty_result` | 调用成功，结果为空 | ❌ **不是失败** | ❌ | 🔴 **正常结果，原样返回。空结果是结论，不是错误。** |
| `unavailable` | transport / timeout / connection refused / 对端 5xx | ❌ | ❌ | "这条证据拿不到：对端不可达（已在传输层重试 N 次）" |
| `refused` | 权限 / policy / scope / caller_policy | ❌ **fail closed** | ❌ | "这是配置里的**故意限制**。" 🔴 **不许说成"查不到 / 无数据"** |
| `duplicate` | 同签名已调过 | ❌ | ❌ | "这个调用刚才已经做过，结果在上面。" |
| `contract_only` | task-bound（`incident_investigate`） | ❌ | ❌ | 🔴 **仍走自己的 preflight/harness，Fast retry 不许绕过** |
| `internal_error` | 未分类异常 / 我们自己的 bug | ⚠️ **最多一次** | ✅（一次） | "我们这边出错了。" ＋ **落 telemetry 到具体字段**，🔴 **不伪装成需要用户补的 gap** |

**三条硬约束：**

1. **枚举封闭。** 新增一类要改代码、改测试，**不能靠自由文本临时表达一个新类别**。
2. **分类由确定性代码做，不由模型做，也不由 LLM 判定。**
3. **未能分类的一律落 `internal_error`**，🔴 **不许落 `bad_arguments`** ——
   因为那会让模型去改一个其实没错的参数（就是 §1 那个死锁的一般形式）。

### 2.3 安全字段白名单 —— 回喂给模型的内容

**允许**（这些模型本来就看得见，或者是纯结构信息）：

| 字段 | 说明 |
| --- | --- |
| `field` | 参数的**公开名字** —— 就是 `TOOLS` schema 里那个名字 |
| `expected` | **来自 schema 的**类型 / 格式 / 枚举。枚举若是敏感集合，只给"枚举，共 N 项，见工具说明" |
| `actual_type` | 实际拿到的**类型和形状**：`str(len=0)` / `null` / `list(len=3)` / `int` |
| `attempt` | 第几次 |
| `failure_class` | §2.2 的八值之一 |

**禁止**：

- ❌ **实际值本身**（可能是 PII、生产标识、告警原文）
- ❌ 内部 rejection code 原文
- ❌ 异常堆栈、文件路径、内部模块名
- ❌ 🔴 **任何"猜出来的"期望值 —— schema 没写就写"未知"**

最后一条要单独说，它是这个项目六轮教训的浓缩：

> **一个编出来的期望值，会让模型自信地把参数改成另一个错的。**
> 外网在示例 JSON 里编过值、给字段安过含义（`55` 说成"存不下引用"，实为"扫过且干净"）。
> **说"未知"是安全的；编一个不是。**

### 2.4 这张表怎么落地（方向，不是实现）

- `TOOLS` 注册表是 `expected` 的**唯一来源** —— 从 schema 生成，不手写第二份。
- 现有自由文本 `error` **不删**（它对人有用），但它**不是**回喂给模型的那份；
  回喂的是结构化的 `{failure_class, field, expected, actual_type, attempt}`。
- 工具**逐个**迁移到结构化错误：先迁**最常被调的那几个**，
  未迁移的一律落 `internal_error`（保守，且不会造成错误归因）。
  🔴 **不要为了一次性覆盖所有工具而推迟这一期。**

## 3. 买回额度 —— 独立计数器，不动 replan

**内网 §4-4 问的是：是独立额度，还是给现有预算对象加字段。**

**定：独立额度。** 理由三条：

1. **概念不同。** replan ＝"换个思路重新规划"；buy-back ＝"同一个计划，参数改对再试一次"。
   合成一个计数器，以后调其中一个必然误伤另一个。
2. **`FAST_MAX_REPLANS=0` 是有意的产品定位**（fast 就该少绕）。
   买回不应该顺手把它改成 5 —— **那就把 Fast 变成 deep 了。**
3. 内网自己也写了："无论选择何者，都必须与真实 replan 分开，且不能放开同参去重。"

**具体：**

- 一个新的独立计数器（名字内网定，例如 `FAST_MAX_REPAIR_ROUNDS`），**默认 2**；
- **只有 `failure_class ∈ {bad_call_syntax, bad_arguments, internal_error}` 才消耗它**；
- 🔴 **`begin_tool_round()` 必须认这个额度** ——
  否则 schema 放开了，预算仍然先把第二轮拒掉（这正是 `FAST_MAX_REPLANS=0` 干的事）；
- **去重规则不动。** 改了参数 → 新签名 → 天然放行；没改参数 → 同签名 → 本来就该挡。
- 额度耗尽 → 正常收尾，**答案里必须出现"试了 N 次仍失败"**，
  🔴 **不许静默退回通用常识**（截图一那个答案的形状，就是静默退回）。

**用户看到的那个 N ＝ 实际发出的 dispatch 尝试次数**，
不是模型轮数，也不是每个工具分别计。理由：模型轮数是内部概念，"我去试了 3 次"才是人话。

## 4. 一份账 —— 权威来源与投影规则

### 4.1 权威

**runtime events 是唯一权威**（`incident_contract_dispatch` / `incident_runtime_entry` /
`incident_mcp_summary` 那一族）。

理由：**它们是执行的副产品，不是事后重建的。**
凡是"根据别的东西推出来的"，一律不能当权威 —— 截图二右侧那个面板就是反例。

### 4.2 投影规则

- `run_steps`、safe debug view **都是投影**，**只许复制字段，不许重构语义**。
- 🔴 **run-step 白名单 / renderer allowlist 要补上这些字段**
  （内网已确认它们目前不在白名单里，所以持久化之后重建不出来）：
  `contract_triggered`、`runtime_entered`、
  `mcp_attempted`、`mcp_executed`、`mcp_failed`、`mcp_suppressed`。
- **新增 `failure_class` 也进这本账**（§2.2）—— 这样 Fast 的买回行为才可复盘。

### 4.3 🔴🔴 unknown 的表示，三层定死

| 层 | 表示 |
| --- | --- |
| 内部 / JSON | `null` |
| API | 字段**保留**，值为 `null` |
| UI | `—` |

🔴 **禁止 `bool(missing)` 和 `int(missing or 0)`。**
内网自己指出 `agent_debug_trace.py` 的 diagnosis projection 就是这么写的 ——
**那两个表达式就是这个 bug 的本体，不是它的症状。**

**这个 bug 的准确形状不是"数字算错了"，是「不知道」被渲染成了「没有发生」。**

### 4.4 一致性测试（这是本节的验收核心）

同一个 `run_id`，四处读**同一个字段**必须一致：

```
runtime events  ==  run_steps  ==  debug/safe view  ==  session reload 之后
```

（"一致"包含"四处都是 `null`"。）

**端到端断言**：一次 **runtime 已进入、MCP 对端失败** 的 run，
面板归因指向**对端**，🔴 **不出现"Harness 未批准"**。

## 7. 不退化基准线 —— 做成 CI，不是一次性检查

**这条防的是下一次。** 这次退化能一路走到业主面前，根因不是谁写错代码，
而是"**Ask 不能比原来差**"这句话从来没被翻译成机器能检查的东西 ——
1668 个测试测的全是管道（返回值形状、权限隔离、脱敏）。

### 基准线 A —— 答案质量

- 同一批 39 条 case，**legacy compat 与 fast 各跑 3 次**；
- 判据：**fast 的「稳定通过集合」⊇ legacy 的「稳定通过集合」**；
- **稳定失败** ＝ 3 次全失败（能力问题）；**波动失败** ＝ 1～2 次（方差，不计入退化判定，但单独列出来）；
- 🔴 理由：上一轮 32/39 vs 31/39，**11 个失败里 7 个是单边的、且两个方向都有** ——
  **单次比较会把方差读成退化，也会把退化藏进方差。**
- 前置：Copilot 可用（502 期间的运行一律标"环境失败"，不产出退化结论）。

### 基准线 B —— 能力面（双口径）

## 9. 明确不做

- ❌ **不松 `answer_gate`。** 它一次都没做错。三个症状是一条链：
  工具调不到 → 没有证据 → 没有可挂的引用 → 答案空泛。
  **闸门是在替上游的证据饥饿背锅。** 松了 = 把"空泛但诚实"换成"自信但错误"。
- ❌ **不改 `normalize_mode()`。** "未知 / 空 → fast" 是对的 fail-safe；
  为止血挖一个"空 → legacy"的洞，正好造出最容易被误触发的规则。
- ❌ **不做用户面的 legacy 回退入口。** 只留一个**非用户面**开关
  （默认关、在 normalize **之后**覆盖、不进 UI、不进 `/api/chat` body 契约），
  唯一用途是双路径评测和排障。
- ❌ **不动 `tool_subset` 和 context lane 份额。**
  tools lane 从 50% 切到 45% 是真的，但绝对值 51485 tokens 不是饥饿。
  **等 P1 落地、工具真的能被调起来之后，如果那时还有截断证据再回来看。**
  现在动它，只会在真正的病因还在时多一个变量。
- ❌ **不重复实现 HKT 文本逻辑**（§6）。
- ❌ **不 reset / restore / stash 并行改动。** 工作树多人并行
  （`agent.py`、`server.py`、`app.js` 有既有修改，多份 Agent 文件未跟踪）。
  **并行踩踏比慢一天贵得多。**

## 10. 本轮不修，但值得顺手做的一件事

内网 §3.1：Agent 那次"0 tool calls、8 model calls、`stop_reason=user_input_required`"，
**角色分布没有保存**。内网提出如果外网要，就新增一份**脱敏聚合导出**，只含：

- `run_id` 的不可逆 / 非敏感关联标识
- 每个 model role 的调用次数
- `user_input_required` 的受控分类 code（如"缺少用户独有目标 / 时间范围 / 业务确认"），**不含问题正文**
- terminal status、`resumable`、工具调用计数

**外网确认这个设计是对的，并且建议顺手做 —— 因为它本来就是 §4「一份账」的天然产物。**
把它当作 **P2 的一个附带产出**，不是一个独立任务。

它能一句话分开两种完全不同的病：

- 8 次**全是 planner** → 编排在原地打转；
- planner 出了计划、**executor 拿不到工具** → 和 §1 是同一个病。

**但它不是 P1 / P2 的阻塞条件**（内网这个判断是对的）。
