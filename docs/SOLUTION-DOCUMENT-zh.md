## 1. 执行摘要

MDC 是银行的**通知投递系统** —— 短信、邮件、App 推送、WhatsApp、微信、信件，全部从这里发给客户。它被拆成了 **460 个 Java 仓库**，后果是：**没有任何一个人知道全貌。**

MDC Assistant 是一个跑在**内网大模型**上的问答助手。你用中文问一句话，它自己去翻代码、翻配置、翻业务路由表、必要时翻生产日志，给你一个**每句话都能点开看出处**的答案。

**它解决的是"检索"问题，不是"模型"问题。** 这一点决定了整个方案的形态：把 460 个仓库喂给大模型是做不到的，也不该做。真正难的是——在 460 个仓库里，怎么把**恰好相关的那几行**找出来递给模型。我们建的就是这一层。**模型和界面随时可以换，这层检索能力才是沉淀下来的资产。**

**现在能干什么（均已在真实数据上验证）：**

| 能力 | 状态 |
|---|---|
| 跨仓库问答 / 改动影响分析 | 🟢 已上线 |
| 业务全链路（用例 → 渠道 → 厂商 → 出口） | 🟢 已上线 |
| 事故影响面（告警 → 谁受影响，零生产访问） | 🟢 已上线，仓库识别率 93.2% |
| 连生产查根因（日志 / 指标 / 投递记录） | 🟡 引擎全通、三台服务真机验证；卡在一张对照表 |
| 生成新模块 / 改一个已有服务 | 🟡 样板路径已跑通（生成 → 编译 → 测试绿 → 出 diff） |
| 自动部署 | ⚪ **有意不做**，银行环境部署永远由人来点 |

## 2. 业务背景与要解决的问题

### 2.1 现状

MDC 这套通知系统由 460 个 Java 仓库组成。仓库之间通过 Maven 依赖和异步消息互相牵连，业务路由规则又存在数据库配置表里。**代码在一边，业务配置在另一边，两边对不上。**

### 2.2 三个今天靠"找那个待了五年的人"解决的问题

| # | 问题 | 今天怎么解决 | 为什么难 |
|---|---|---|---|
| 1 | 我改这个公共模型，会连累谁？ | 人工翻 pom、问老同事 | 依赖关系散在 460 个 `pom.xml` 里，没人能手工数完 |
| 2 | 这条通知到底怎么走到客户手机上的？ | 一半查代码、一半查数据库，靠人脑拼 | 答案跨越代码层和业务配置层，没有工具同时看得到两边 |
| 3 | 凌晨这条告警是谁的事？要不要叫业务方起床？ | 值班人自己判断 | 告警只说了某个服务 CPU 高，说不出这影响哪些业务用例 |

### 2.3 结论

**这三个问题的答案分散在四个互不相通的地方，而且没有任何一个现成工具能同时看到这四层。** 这就是本方案存在的理由。

## 3. 范围

### 3.1 在范围内

- 跨 460 个仓库的代码理解、依赖影响分析、真实调用链
- 服务之间的异步消息布线（谁产、谁消）
- 业务用例 → 渠道 → 厂商 → 出口的全链路解释
- 事故的业务影响面分析与根因调查
- 新服务脚手架生成、对已有服务的模板化改动（生成后交人评审）

### 3.2 明确不在范围内（这四条是设计决定，不是没做完）

| 不做什么 | 为什么 |
|---|---|
| **不自动部署** | 银行环境。部署这一步永远由人来点，不追求 AI 自主 |
| **不写生产数据** | 全程只读。对生产代码库、生产数据库、生产日志，一个字节都不写 |
| **不重建已有的 AIOps 1.0** | 团队已有一套规则式告警处置系统，做得不错。我们做的是它答不了的那一层（为什么挂、影响谁），不是替代它 |
| **不猜** | 查不到就说查不到。**"没去查"和"查了没发现"必须分开说**，绝不用推断冒充证据 |

## 4. 方案总览

### 4.1 四层架构

助手的价值来自于**把四层原本互不相通的东西接在了一起**：

| 层 | 里面是什么 | 回答什么问题 | 数据性质 |
|---|---|---|---|
| ① **代码层** | 460 个仓库的源码、依赖图、跨仓库调用链 | 改这个类会连累谁？谁调用了它？ | 我们自建的索引 |
| ② **消息层** | 服务之间的异步布线：谁往哪个主题发、谁在收 | 这条消息从哪来、到哪去？ | 我们自建的索引 |
| ③ **业务层** | 用例、渠道规则、厂商路由表 | 这条通知走短信还是邮件？交给哪家厂商？ | 业主的配置数据 |
| ④ **运行层** | 生产日志、监控指标、投递记录 | 它昨晚 3 点为什么挂了？这条通知到底发出去没有？ | **实时连生产取** |

**为什么四层接起来才有价值**：单看任何一层都答不了真正的问题。
代码告诉你"这个仓库依赖那个仓库"，但答不了"所以哪个业务受影响"；
业务表告诉你"这个用例走短信"，但答不了"短信服务的代码是哪个仓库、它昨晚报了什么错"。

> **把这四层串起来的那条线，就是本项目真正的资产。**

### 4.2 前三层 vs 第四层的根本区别

这个区别在合规上必须讲清楚：

- **①②③ 层是我们自己预先建好的索引**（离线构建，只读，不碰运行中的系统）
- **④ 层是请求发生时才实时连到生产系统去取**

所以任何一个回答里，来自 ①②③ 的部分和来自 ④ 的部分，**风险等级完全不同**，助手在答案里也是分开标注的。

## 5. 系统是怎么产生一个回答的

### 5.1 机制：模型不"背"代码，它是个「会用工具的人」

常见误解是"把 460 个仓库喂给大模型"。做不到，也不该做。实际机制是：

```
你问一句话
   ↓
助手判断该查什么（选工具 + 定参数）
   ↓
调用检索工具，去查预先建好的索引 / 实时查生产
   ↓
拿到真实结果
   ↓
带出处回答你
```

**这带来一个重要后果：它答不上来的时候会说答不上来，而不是编一个。** 因为答案不是"想"出来的，是"查"出来的 —— 查不到就是查不到。

### 5.2 运行时组件流

```
浏览器
  ↓
webapp/server.py          （HTTP 服务，纯标准库）
  ↓
webapp/agent.py           （工具调用循环：判断查什么 → 调 → 拿结果 → 再判断）
  ├→ webapp/llm.py        → 内网大模型（唯一的模型出口，门面模式）
  └→ webapp/tools.py      → retriever/  （检索层，21 个工具）
                          → CodeGraph  （跨仓库真实调用链）
                          → webapp/mcp_client.py → 三台 MCP（运行层，实时）
                          → webapp/db_readonly.py → UAT 只读库（命名查询，模型不写 SQL）
```

### 5.3 每句话都带出处

答案里每个结论后面都跟一个**可点击的引用**，点开直接看到那一行源码或那一行配置。

> **你不需要相信助手，你只需要点开看。**

## 6. ⭐ 数据流与溯源 —— 每个结论从哪来

> **这是全文最重要的一节。** 它逐跳回答："助手说 K3002 走短信、交给某家厂商、走某个主题、最后从某个出口发出去 —— 它凭什么这么说？"

### 6.1 旗舰链路：用例 → 渠道 → 主题 → 投递 → 出口 → 回执

这是助手最常被问、也最能体现四层价值的一条链：

```
业务用例
   ↓  ①
渠道规则（发短信还是邮件？先发哪个？失败了发谁？）
   ↓  ②
权威路由表（厂商 / SLA / 投递等级）
   ↓  ③
消息主题
   ↓  ④
投递任务
   ↓  ⑤
出站 API
   ↓  ⑥
厂商 → SMSC / APNs / 邮件网关 / 打印出口
   ↓  ⑦
投递回执（这条到底发出去没有？）
```

### 6.2 逐跳数据来源表 —— **本节的核心**

| 跳 | 助手会说什么 | 数据从哪来 | 数据的性质 | 可信度 |
|---|---|---|---|---|
| ① **用例基本信息** | 这个用例属于哪个业务类别、owner 是谁 | 业务用例主表（UAT 只读库 / 已导出快照） | 业主维护的配置数据 | **权威** |
| ② **走哪些渠道、什么顺序** | 「先发短信，失败了才发邮件」 | 渠道规则表里的规则表达式，由我们解析 | 业主配置 + **业主已确认的表达式语义**（2026-07-27） | **权威** |
| ③ **哪家厂商 / SLA / 投递等级** | 「交给某家厂商，SLA 60000 毫秒」 | 权威路由表，用四列自然键连接（业务类别＋渠道＋route＋router） | 业主配置 | **分四档，见 6.3**。实测只有 **27.3%** 能拿到权威厂商 |
| ④ **走哪个消息主题** | 「进短信主题」 | 提交在库的 7 列架构节点目录（含边）＋ 从 460 个真实仓库名解析出的交付拓扑 | **架构事实** | 事实。解析器经 4 轮真机验证 |
| ⑤ **哪个投递任务仓库** | 「由某个 deli-job 仓库消费」 | 同上（仓库名解析 + 依赖图） | **代码事实** | 事实，可点到具体仓库 |
| ⑥ **出口是什么** | 「最后从某电信商的 SMSC 出去」 | 架构节点目录的终端列 | **架构事实** | 事实 |
| ⑦ **这条到底发出去没有** | 「这条 tracking id 的投递结果是 X」 | **投递记录平台（MCP），请求时实时查生产** | **运行时真相** | 实时证据；**查不到会明确区分"没去查"和"查了没有"** |

**读这张表要抓住的三件事：**

1. **④⑤⑥ 是"事实"** —— 管线长什么样、哪个厂商服务哪个渠道，这是架构，不是猜的。目录提交在库里，拓扑从真实仓库名解析，解析器被内网真机验证过四轮。
2. **③ 是整条链上最弱的一环**，而且是**源数据的限制，不是引擎的限制**（见 6.3）。
3. **⑦ 是唯一实时连生产的一跳**，风险等级和前六跳完全不同，所以在答案里单独标注。

### 6.3 为什么"哪家厂商"要分四档 —— 以及实测数字

**结论分档，不把"猜的"和"查到的"混在一起。** 助手每次说厂商，都会带上它是哪一档：

| 档 | 含义 | 助手怎么说 |
|---|---|---|
| **权威** | 权威路由表匹配上了，且厂商显示名已被业主确认 | 「就是这家」 |
| **权威但名字未确认** | 权威行匹配上了、也确实写了厂商名，但这个显示名还没有业主确认的规范化对应 | **原样引用那个字符串**，不指向任何一个厂商节点 |
| **提示** | 渠道规则的 route/router/sender 列里出现了已知厂商名 | 「提示是这家，但这几列是否真的承载厂商信息尚未验证」 |
| **上界** | 拿不到具体厂商，只能给出该渠道上的所有厂商 | 「**最多**这几家」，**绝不说"就是这家"** |

**为什么必须这样做——实测数据（真实 UAT 导出）：**

| 指标 | 实测值 |
|---|---|
| 权威路由表总行数 | 247 |
| 子行的四列键能连上的比例 | 49.79% |
| 其中落在非空厂商上的比例 | 54.87% |
| **⇒ 最终能拿到权威厂商的比例** | **约 27.3%** |
| 表里出现的不同厂商值 | **只有 4 个**，且只覆盖推送和短信 |
| 厂商列为空的行占比 | 58.70% |

**对邮件、信件、WhatsApp、微信这四个渠道，权威厂商列是完全空的** —— 所以"上界"这一档对它们不是权宜之计，**它是唯一存在的答案**。

> **设计原则：一个诚实的宽答案，好过一个自信的窄答案。**
> 多列几家厂商，读者多花一句话；说错一家厂商，凌晨三点叫错人。

### 6.4 两个被真实数据纠正过的认知（值得单独讲）

这两条都不是理论推演，是**在真实数据上被证伪后改掉的**：

**① 流量 0% 的厂商不是"关掉了"，是备用。**
配置里 `流量=0%` 的那一行，是**故意配的第二家厂商**，也就是主力挂掉时接管的那一家。
真实数据：**897 个渠道是"正在发 + 背后有一个 0% 备用"**。
修正之前，问"主力厂商挂了谁接管"，这 897 个渠道**一个都答不出来**。

**② 发送顺序是有业务语义的。**
规则表达式里 `>` 表示"左边失败了才发右边"、`&` 表示"一起发"、`|` 表示"二选一"。
这意味着：**前一级正常的时候，后面那些渠道根本没在发** —— 影响面不能把它们全算成活流量。

### 6.5 事故这条线的数据流（左右两半，风险不同）

```
        把告警原文粘进来
              │
   ┌──────────┴──────────┐
   │                     │
【谁受影响】          【为什么挂】
零生产访问            连生产查证据
   │                     │
识别仓库 93.2%      ┌────┼────┐
   │                │    │    │
涉及哪些主题      日志  指标  投递记录
   │                └────┼────┘
哪些业务用例             │
   │                 脱敏证据包
哪些渠道 / 通知谁        │
   └──────────┬──────────┘
              │
     一个带出处的完整回答
```

**左右两半是故意分开的两个功能，因为风险完全不同：左边一个生产字节都不读，右边真的连上去。任何时候都不能把左边的推断说成右边的证据。**

### 6.6 运行层接的三台服务（**不只是查日志**）

这是最容易被简化掉的一点。实际接了三台，各自回答完全不同的问题：

| 服务 | 里面是什么 | 回答什么问题 | 调用前必须先知道什么 |
|---|---|---|---|
| **日志平台** | 各应用的异常日志、链路日志 | 「它报了什么错？」 | 应用名 **+ 时间窗（必须带时区）** |
| **指标平台** | 告警定义 + 监控指标曲线 | 「挂之前曲线是什么形状？」 | 告警名 + 时间窗 |
| **投递记录平台** | 单条消息的投递结果 | 「这条通知到底发出去没有？」 | **只要一个 tracking id** |

⭐ **一个必须知道的事实**：**最大的那一族告警里，既没有仓库名，也没有告警名。** 日志和指标都拿它没办法，**只有投递记录这条路能查**。所以把运行层简单理解成"查日志"，会正好漏掉最重要的那一条。

三台服务**全部真机验证过，工具名零偏差**。

> ⭐ **关键不在于"能连上"** —— 连日志谁都能连。
> **关键在于它知道该查什么**：查哪个应用、哪些关键词、哪个时间窗，
> **全都是从前三层推导出来的**。这才是四层接起来的价值。

## 7. 技术栈

### 7.1 一句话

**前端：原生 HTML / CSS / JavaScript，没有框架、没有构建步骤。**
**后端：Python 3，只用标准库，没有任何第三方依赖。**

整个系统**装不上也不需要装任何包** —— 这不是省事，是为了能在隔离网环境里直接跑（见 7.5）。

### 7.2 选型总览

| 层 | 用了什么 | 选型理由 |
|---|---|---|
| **前端** | 原生 HTML / CSS / JavaScript，无框架、无构建、无 npm | 部署 = 拷一个目录；浏览器不发一个外部请求 |
| **后端** | Python 3，**纯标准库、零第三方依赖** | 隔离网直接跑：不需要 pip、不需要过依赖审批、不引入供应链风险 |
| **模型接入** | 内网大模型，OpenAI 兼容 HTTP 接口 | `webapp/llm.py` 是**唯一**的模型出口（门面模式），底下 3 个 provider 可插拔 → **模型随时可换，其余代码零改动** |
| **检索层** | 预建索引产物（依赖图 / 消息图 / 仓库标签 / 交付拓扑），落地为 **JSON + CSV 文件** | 离线构建、只读查询。一次建好、多次查询；**我们自己不部署任何数据库** |
| **调用链** | CodeGraph（外部 CLI，按业务域分包索引） | 单个图放不下 460 个仓库 → 必须按域切分，配合"先收窄再检索"；CLI 不在 PATH 上时**如实降级**，不伪造结果 |
| **业务数据** | 业务配置表导出快照 + UAT 只读库直连 | 快照保证可离线；直连保证时效 |
| **运行层** | 自研 MCP 客户端（2 种传输、3 道闸门） | 对接同事维护的三台 MCP 服务 |
| **数据库访问** | **命名查询**机制；**驱动不在我们这边** | ⭐ 见 7.4 |
| **配置缝** | `config/` 下 8 个 JSON 配置文件 | ⭐ 内网同事改配置就能调，**不用等外部推代码**（见第 9 节） |

### 7.3 前端具体用了什么

| 项 | 实现 |
|---|---|
| 页面 | 单页应用，3 个文件：`index.html`（268 行）、`app.js`（2,162 行）、`app.css`（1,457 行） |
| 框架 | **没有**。不用 React / Vue / jQuery，不用打包器，不用 npm，没有构建步骤 |
| 与后端通信 | 浏览器原生 `fetch()` |
| **流式输出** | `fetch()` + `ReadableStream.getReader()` **增量读取响应体** —— 回答一边生成一边显示，工具调用的进度实时出现在界面上 |
| 唯一的第三方前端资源 | **`mermaid.min.js`，本地自带，不走 CDN**（用于把助手输出的架构图渲染成图） |
| 缺了它会怎样 | **优雅降级**：文件不在就不渲染，图直接以源码文本显示。不报错、不需要改代码 |

> **要点：浏览器不向外部发任何一个请求。** 所有静态资源都由后端本地提供。

### 7.4 后端具体用了什么

| 项 | 实现 |
|---|---|
| HTTP 服务 | 标准库 `http.server.ThreadingHTTPServer` + `BaseHTTPRequestHandler`，路由是手写的 `do_GET` / `do_POST` |
| 并发 | 每请求一线程（标准库自带） |
| 对外 HTTP 调用 | 标准库 `urllib.request`（调模型、调 MCP、代理检索服务） |
| 数据落地 | **JSON / CSV 文件**。会话、反馈、索引产物都是磁盘上的文件 —— **我们自己不跑任何数据库** |
| 调外部程序 | `subprocess` 调 `codegraph` CLI |
| **数据库驱动** | ⭐ **我们的代码里没有数据库驱动。** `webapp/db_readonly.py` 通过环境变量给出的路径导入**内网自己的 runner 模块**，只调它交接文档指定的两个函数 —— 所以 `psycopg` 之类的驱动**从来不会被我们的核心 import**，核心保持纯标准库 |
| **模型不写 SQL** | 模型只能选一个预定义的**查询名** + 传绑定参数。SQL 文本、schema、表名、**列白名单**全在配置文件里；**PII 列只要不写进白名单，就永远出不去** |

### 7.5 为什么坚持"零依赖"（这是个刻意的决定，值得说一句）

| 好处 | 说明 |
|---|---|
| **能在隔离网跑** | 不需要 pip、不需要内网镜像源、不需要走依赖审批流程 |
| **没有供应链风险** | 没有第三方包 = 没有第三方包的漏洞要跟、要打补丁、要过安全扫描 |
| **部署成本极低** | 部署 = 拷一个目录 + 跑一条 Python 命令。给团队用 = 在一台内网机器上设好 host/port，同事开浏览器就行，**不需要装任何东西** |
| **升级不会坏** | 没有版本冲突、没有 `npm install` 失败、没有构建产物过期 |

## 8. 安全与合规

### 8.1 姿态总结（一句话能讲完的版本）

**只读生产 · 数据不出网 · 每条结论可核对出处 · 生成物只在草稿区 · 纯标准库适配隔离网。**

### 8.2 逐条说明

| 项 | 做法 |
|---|---|
| **只读** | 对生产代码库、生产数据库、生产日志，全程只读。数据库连接走**只读事务**，且每次都在本地复核这一点 |
| **不出网** | 模型跑在内网。没有任何数据离开网络 |
| **SQL 不由模型生成** | 模型只能选预定义查询名 + 传参。SQL 文本、schema、表名、列名**白名单**都在配置里。**PII 列只要不写进白名单，就永远出不去** |
| **未配置 = 拒绝执行** | 配置里留 `?` 的查询会被**拒绝执行**，助手会明说"这条查询还没接通"，**绝不会拿一条猜的 SQL 去查，也绝不会把"没接通"说成"库里没这条记录"** |
| **生产日志脱敏** | 三层脱敏。**原始日志永远不进入模型上下文、也不进入会话历史** —— 只有分类后的结构化证据包离开进程 |
| **生成物隔离** | 生成的代码只写进草稿目录，**绝不碰生产仓库**；参考服务里的账号、团队、内部 URL、组织业务码等治理值**自动打码** |
| **凭据不入库** | 数据库地址、账号、token 不在这个代码库的任何地方，连接完全由内网侧负责 |
| **默认关闭** | 新增的数据通路默认不可调用，开放必须是一次**明确的配置编辑** |

## 9. 交付与协作模式（内外网的缝）

> 这一节解释「一个隔离网项目是怎么被开发出来的」。这套流程本身是项目资产的一部分。

### 9.1 约束

**内网推不了代码。** 这个约束决定了整个协作模式。

### 9.2 流程

```
外网：写代码 / 写规格
   ↓  push
内网：拉取 → 在真实环境跑验证手册（RUNBOOK）
   ↓  回执（照片 / 文字）
外网：按回执修 → 再 push
```

**已经这样跑了 71 轮。**

### 9.3 关键设计：**责任划分靠配置文件，不靠改代码**

因为内网推不了代码，所以**凡是"只有内网才知道的东西"，一律走配置文件**：

| 谁知道 | 放在哪 |
|---|---|
| 真实的表名、列名、SQL | `config/db_queries.json`（内网维护本地副本） |
| 真实的 MCP 工具名、参数、返回结构、时间格式 | `config/mcp_tools.json` |
| 业务枚举、渠道证据、告警模式、术语表 | `config/*.json` |

**结果：内网改一行配置就能调整行为，不用等外部推代码。**

配套的两条纪律：
- 被 git 跟踪的那份模板**永远全是 `?`**，不含任何真实表名、列名、schema
- 内网改**本地副本**（已在 `.gitignore` 里，程序自动优先读它）—— 否则下一次 `git pull` 会因为跟踪文件有未提交改动而**整个被拒绝**，挡住的不只是这个配置，是那次 pull 里的所有修复

### 9.4 这套流程带来的最大收益

**每一轮验证都抓到了真缺陷，而且缺陷有固定形状：**

> **几乎每一个缺陷，都是"我们对他们的环境做了一个断言"** —— 断言了名字、断言了返回结构、断言了值的格式。
> **修法一律相同：抽象的部分我们留着，真实的名字、结构、格式全部交给内网。**
