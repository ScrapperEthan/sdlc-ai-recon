> ### ⭐ 2026-07-30 更新：内网 Codex 现在可以通过 skills 直连 UAT 数据库
>
> 这条改变了下面**一半以上**的申请形态。原先很多项写的是"请 DBA 导出 XX"，
> 其真实需求是"**我们需要知道某个事实**"——而现在内网可以**自己去查**。
>
> **重新分类**（下面每个案例里已按此标注）：
>
> | 类别 | 原来的做法 | 现在的做法 |
> | --- | --- | --- |
> | **可自查（UAT 库里有）** | 提工单等 DBA | **内网 Codex 直接查，当天出结果** |
> | **仍需 DBA** | 同上 | 只剩：**同一时刻一致性快照**（自查是逐表查，解决不了 `mixed_export_times`）、以及**生产库**的任何东西 |
> | **仍需业务方** | 同上 | 不变——语义问题（`delivery_path` 含义、`vendor` 为空是什么意思）查库查不出来 |
> | **仍需平台/安全** | 同上 | 不变——IAM/KMS/CI/事故记录都不在 UAT 库里 |
>
> **由此产生的三个新方向（建议内网 Codex 优先探索，都不需要等任何人批）：**
>
> 1. **直接把"表结构"问题问掉。** 案例 1 和 3 卡在"消息主表/状态表/回执表/幂等表长什么样"。
>    如果 UAT 库里就有这些表，那 `information_schema` 一查即得：表名、列、主键、唯一键、索引。
>    **这一项能一次解开案例 1 的落库段和案例 3 的幂等判断**，是当前性价比最高的探索。
>    请回报：表名清单 + 关键表的列结构 + **唯一约束**（唯一约束是幂等的直接证据）。
> 2. **把 `vendor` 为空的 145 行分组统计一遍。** 语义要业务方确认，但**分布**可以自查：
>    这 145 行集中在哪些渠道 / 哪些 business_category / 哪些 route？
>    如果它们整齐地落在 email/letter 上，那"该渠道没有厂商概念"这个解释就基本成立，
>    去问业务方时可以带着答案去确认，而不是开放式提问。
> 3. ✅ **`tbl_event_router_usecase_topic` 在 UAT 库里确认存在**（内网 2026-07-30）。
>    **这是当前最大单点阻塞的一半解开了。** 但注意**剩下的一半仍然要 DBA**：这张表必须和另外
>    四张表**同一时刻**取，否则连接仍是跨时间连接。所以申请内容从"导五张表"变成
>    "**取一次同时刻的一致性快照**"——工单更小、更容易批。
>    请先回报：UAT 里的行数、topic 去重数，以及和现有 dev/SCT 快照（20 个 topic）的重合数。
>    重合数是判断"精确 repo→use case 那一跳能补多少"的直接依据。
>
> **一个纪律提醒**：能自查不等于可以把结论当"生产事实"。UAT ≠ 生产，
> 任何从 UAT 得出的覆盖率/分布，对外表述时都要带上环境标注——
> 这一点助手已经在代码层面强制了（同环境闸门），人工回报时也请保持同样口径。

## 一、一页结论

**能力现状**：8 个案例里，**4 个现在就能演**（案例 1、4、5、8），2 个能演一半（案例 2、7），
2 个只能演到"提出正确的问题"（案例 3、6）。

**最大的三个阻塞，按解开难度从低到高：**

| 阻塞 | 影响哪几个案例 | 解开需要 | 代价 |
| --- | --- | --- | --- |
| **① 四张 UAT 表不是同一时刻导出**，且 `tbl_event_router_usecase_topic` 只有 dev/SCT 版 | 1、2、5、8 | DBA 一次同时间点导出 | **一次请求，最高性价比** |
| **② 服务 ↔ LogDream 应用名 没有权威对照** | 5、6 | 一个映射文件（98 个应用对 460 个仓库，实际只需要热点那 20 个） | 内网半天 |

**一句话**：现在的瓶颈**不是引擎能力**，是**同环境的数据**和**运行时事实**。
引擎侧今天已经能把"代码 + 配置 + 业务路由 + 生产日志"四层接起来并逐条标注可信度。

> ### ⚠️ UAT 内测期的一个例外（业主决定 2026-07-30）
>
> devops 内测需要**能核对调查员有没有编造**，所以加了一个**默认关闭**的开关
> `SDLC_INCIDENT_RAW_LOGS`。打开后每条证据可以点「查看原文」读未脱敏日志。
>
> **打开它改变了什么、没改变什么，要能一句话说清：**
>
> | | |
> | --- | --- |
> | **改变** | 原始日志会**留存在服务器磁盘上**（`webapp_data/incident_raw.json`，单独文件、默认 72 小时、最多 200 条、每条最多 500 行），浏览器可按需取回 |
> | **不变** | **模型仍然只收到脱敏聚合结果**。原文不进模型上下文，也不进 `chat_sessions.json` |
> | **访问控制** | 取原文按会话归属鉴权（和聊天记录同一套）；换一个浏览器取同一个 ref 返回 404，与"不存在"不可区分 |
> | **可删除** | 一个 API 一键清空，或直接删那一个文件。不用动聊天记录 |
>
> **为什么不直接存进 `chat_sessions.json`**（业主原话是想存那里）：会话记录每一轮都会被
> **重放回模型**（`history_for_agent`），所以存那里等于**后续每一轮追问模型都会重新读到未脱敏日志**——
> 那正是整套设计要防的事。放在单独文件里，业主要的可追溯性一样拿到，但不带这个副作用。
> 如果确实需要原文随会话一起导出，告诉我，我再加一条导出时合并的路径。
>
> 🔴 **正式使用前必须关闭。** 前端在开启期间会持续显示红色提示条，说明原文正在留存。

### 案例 2：为什么选择供应商 A

**现在能演到什么程度：约 60%**

能准确回答**配置上是怎么选的**：`rule_text` 的运算符语义已经业主确认（`>` 左边先发、`&` 一起发、
`|` 二选一，且 **`rule_text` 权威、`priority` 只在 rule_text 为空时兜底**）；四列自然键
（`business_category + channel + route + router`）连到权威路由表，拿到厂商原文、SLA、delivery_path；
厂商答案分四档可信度，逐档说明为什么不能更强。

**硬数字（这些要在汇报里说清，否则会被当成"数据不全"）：**

- 权威路由表 **247 行**，其中 `vendor` 为空 **145 行 = 58.70%**
- 子表回连成功 **2967 / 5959 = 49.79%**（`tbl_use_case_channel_rule` 共 6217 行，258 行四列键不完整）
- 因此**能拿到权威厂商的只有约 1628 / 5959 ≈ 27.3%**
- `vendor` 全部取值只有 4 个：`HTCL` 70 行 / `AWS SG SNS` 16 / `AWS HK SNS` 7 / `HTCL OLD` 9
  → **只覆盖 push 和 SMS**。email / letter / whatsapp / wechat 的权威厂商**完全没有**，
  那几个渠道的"渠道级上界（最多这几家）"不是过渡方案，**是唯一存在的答案**

**卡在哪：**

1. 🔴 **厂商显示名的 canonical 映射没有业主签认。** 内网已给出**有据的建议**
   （`AWS HK SNS`→`awshk`、`AWS SG SNS`→`awssg`、`HTCL`→`3hk`，`HTCL OLD` 保留原文 + 标 legacy），
   而 `awshk`/`awssg` 本来就在我们的厂商白名单里，所以这是**可核对的映射，不是猜测**。
   但内网明确写了"**router 表语义仍需业主确认**"——即路由表里的 `HTCL` 是否就是仓库命名里那一家。
   **所以代码里目前 0 条内置别名**，助手只能原文照抄"权威表记录 `HTCL`"，不能说"它走 3HK"。
2. 🔴 **`delivery_path` 1–9 没有文字码表。** 已确认它是**分类元数据**（同名字段还出现在
   `tbl_template`、Template API request、adhoc campaign、SMS billing report），

4. 🟡 **有没有独立的主备 / fallback 配置表**。
5. 🟡 **厂商健康 / 限流 / 熔断 / 价格数据**在哪：CloudWatch 指标？Resilience4j actuator？配置中心？

### 案例 3：超时后是否重复发送

**现在能演到什么程度：约 20% —— 这是 8 个里最弱的，建议汇报时明确降低预期**

能做到的：定位到全部相关仓库（`api-kafka-sdk`、`commonbus-sdk`、`api-cloud-client`、
`delivery-core`、`rest-invoker`、`resend-core`、`resend-api`、`event-router-replay-api`），
扫出 `@Retryable` / Resilience4j / Kafka producer retries / `RestTemplate` timeout / `payloadUuid`
这些点，并给出"**存在重复风险**"的结论。

**为什么到不了"确定会重复"**：这需要四种我们现在没有的分析能力——

1. 异常传播分析（异常从哪抛、被谁吞、是否触发重试）
2. 事务边界与 ACK/commit 分析（消息确认与 DB 提交的先后）
3. 幂等键生命周期分析（`payloadUuid` 是否真的贯穿到厂商侧）
4. 故障注入验证

前三项是**周级的引擎研究工作**，第四项需要环境。**在没有故障注入或历史事故证据前，
任何"确定会/不会重复"的结论都是不负责任的**——这一点内网的分析也是同样结论。

**需要申请：**

| 要什么 | 为什么 | 找谁 |
| --- | --- | --- |
| 消息去重/幂等表的 DDL + 唯一约束 | 幂等到底靠 DB 约束还是靠代码，决定结论方向 | **DBA** |
| Kafka/CommonBus 的 `retries` / `acks` / `enable.idempotence` 实际值 | 生产实际配置，不是代码默认值 | **MDC 运行团队 / 配置仓库** |
| SQS 的 `visibility` / `maxReceiveCount` / redrive 策略 | 部分可从 CloudWatch MCP 自查，但 IaC 更准 | **平台团队** |
| **厂商 API 是否支持幂等 ID、超时后能否按 request ID 反查** | 🔴 这是最关键一条：厂商不支持幂等，则重复不可避免 | **厂商接口人** |
| 3–5 个已完成、可脱敏的**真实超时事故记录** | 有历史证据才能从"存在风险"升级到"曾经发生过" | **事故管理 / MDC 运行团队** |
| 人工重放到底在哪个页面执行、重放前是否查历史状态 | 决定"人为重复"这条路径 | **MDC 运行团队** |

### 案例 5：CloudWatch 告警根因定位

**现在能演到什么程度：约 70% —— 这两天提升最大，建议作为演示主线**

完整链路已经通了：

```
告警文本 → 识别仓库（真实数据 93.2%）
```

三台 MCP 全部真机验证通过（RUNBOOK-60）。关键词不是"搜 ERROR"，是**从我们代码图和业务图推出来的**：
那个仓库真实会抛的异常类、它产/消的主题、它服务的渠道——**这是通用 AIOps 推不出来的部分**。

2. 🟡 **3–5 个可脱敏的真实事故样本**，用于验证整条链而不是只验证连通性。

   LogDream 也 0 命中）。但**Portal MCP 现在通了（55 个工具）**，那一族的 trackId 排查路径已经可达。

**需要申请：**

### 案例 8：核心节点 Top 10

**现在能演到什么程度：约 60% —— 已建好，今天就能演**

新建的 `critical_repos` 做的是**多维评分**，不是一个总榜。原因值得在汇报里说一句，
因为它是"看起来对但其实错"的典型：

> 按 Maven 依赖数排序，`api-common` 一定第一（所有人都依赖它，但它不承载任何消息）；
> 而一个投递任务承载了全行所有短信，却没有任何仓库依赖它。
> **一个总榜会悄悄替听众选了一种"核心"的定义。**

**能算的 3 个维度**：依赖中心度（Maven 直接依赖者数）、消息中心度（产/消的主题数）、
业务影响面（经由其主题的业务用例数）。每个维度单独给排名，合并分只是"现有维度的一个等权视图"。

**明确标为算不了的 3 个维度**（结果里每次都会带上，含各自的 owner）：

| 维度 | 为什么算不了 | 需要什么 | 找谁 |
| --- | --- | --- | --- |
| **生产流量** | CloudWatch 有按资源的指标，但资源↔仓库没有连接，且 460 个仓库逐个查（单次约 26 秒）不是可运行的查询 | 告警/资源 ↔ 仓库对照表 + 我们写一个批量采集 | **平台团队** + 我们 |
| **故障历史** | 记录在 ServiceNow / AIOps 告警库，我们不读 | 固定时间窗内按服务的事故数导出 | **事故管理 owner** |
| **测试覆盖** | 在 CI 报告里（JaCoCo/Surefire），不在源码镜像里 | 每个仓库的 `jacoco.xml` | **CI/CD owner** |

另外两个可选增强：**代码 owner**（仓库 CODEOWNERS，我们可自查）、
**业务 owner**（`tbl_use_case_ext.message_owner`，已有数据）。
