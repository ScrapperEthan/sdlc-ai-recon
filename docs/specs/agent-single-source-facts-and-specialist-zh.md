## 1. 直接病因 —— 时区这个事实没有唯一来源

### 问题

`timezone` / `alert_time` 现在是**由模型生成的参数**：规划那一步的模型写一个，执行那一步的模型再写一个。
两个值不一致时，你们的闸门（回报里叫 scope gate，**请以你们的真实名字为准**）把这次调用挡掉了。

闸门做得对 —— 执行超出计划范围本来就该拦。**错的是让两个模型对同一个事实各表述一次。**

### 不改的后果

时区是这个项目里**最不能猜的一个参数**，理由不是洁癖，是它错了不会报错：

- CloudWatch 写 UTC，LogDream 默认 Asia/Hong_Kong，服务器是 GMT ——
  **同一个 03:15 是相隔 8 小时的三个时刻**；
- 查错时刻**不会失败**，它返回空；
- 而**空会被读成"日志是干净的"**。

也就是说，今天这个 bug 的运气其实是好的：**它被闸门挡住了，所以你看见了。**
换一种走法 —— 两个模型碰巧给出**同一个错值** —— 闸门会放行，
然后系统拿着一份**无关时段的生产日志**给出一个自信的错误根因。
这跟 2026-08-04 那次 LogDream「keyword 没命中 → 服务端静默回文件尾部」是**同一个形状**：
一次静默的错配，产出一个像模像样的结论。

第二个后果：这一次调用花掉的是**打在同事服务器上的生产查询预算**；用户等完之后，
拿回来的是一个内部参数不一致，而且从答案上看不出这是我们自己的问题。

### 改完的效果

- 一轮里**只有一个地方**能回答"这次查的是哪个时刻、哪个时区"，两个模型都从那里读；
- 那个地方回答不了的时候，用户看到的是**一句话的问题**（「这个 03:15 是 HKT 还是 UTC？」），
  不是一个内部拒绝码；
- 台账里能直接读出这个值**从哪来**（告警原文 / 用户说的 / 没有）。

### 具体怎么改（三条，都很小）

#### 1.1　这类参数由确定性代码解析一次，模型不许 emit

外网快照里这个解析器**已经存在，而且优先级已经定义好了**
（`webapp/incident_plan.py` 里建 window 的那一段，配 `webapp/incident_parse.py` 的时间抽取；
你们那边的对应位置以实际为准）：

```
时刻(stamp)：告警原文里的显式时间戳  >  调用方传入的 alert_time  >  没有 → BLOCKING
时区(zone) ：告警原文里的显式时区    >  调用方传入的 timezone    >  没有 → BLOCKING
```

其中一条注释就是为这次这种情况写的：
**「告警原文里的时区优先于调用方传的，因为告警本身才是证据」**。
换句话说，**"两个来源不一致"这件事，解析器早就有裁决规则了 —— 缺的是让两个模型都走它。**

- planner **不产出** `timezone` / `alert_time`，它只产出"要不要走 incident 这条能力"；
- executor **不产出** `timezone` / `alert_time`，它从台账读；
- 两半**分开判、分开报**（现有实现这一点是对的，别合并）：缺日期问「哪一天」，缺时区问「哪个区」——
  在事故中间问错一个，就白跑一个来回。

#### 1.2　解析结果作为一条 fact 落进台账，带出身

```json
{
  "fact": "incident_window",
  "alert_time": "2026-07-30 03:15:00",
  "timezone": "Asia/Hong_Kong",
  "source": "explicit in the alert text | user-supplied | absent",
  "resolved_by": "deterministic parser",
  "evidence_id": "..."
}
```

这条 fact 就是"共享 memory"在这件事上的**全部含义** —— 不是共享对话，是**共享结论 + 出身**。
台账已经落盘了，这条挂上去几乎零成本。

#### 1.3　给"不许模型生成"的参数立一张封闭清单

判据只有一条：**猜错了会静默产出一个自信的错误答案的参数，一律不许模型生成。**

| 参数 | 谁产出 | 猜错了会怎样 |
| --- | --- | --- |
| `alert_time` / `timezone` | 确定性解析器（本节） | 查到无关时段 → 空 → 被读成"没问题" |
| `alarm_name` | 用户给的 > 告警原文严格提取，**没有第三种** | 返回**另一个服务**的指标，挂在这次事故的标题下 |
| `app` / `source` / `file` | 代码从 repo id 映射 / 配置里的实际取值 | 查了别人的日志；或整个分支静默跳过 |
| repo id | 校验 against 仓库全集，未知一律拒 | 编出一个不存在的仓库，nil 结果看起来像结论 |
| `tracking_id` | **只能是用户给的**（出口会指纹化） | 查到别人的投递记录 |

模型**可以**产出的：`keywords`（但必须标成 user/model-supplied —— nil 结果的含义完全不同）、
`max_queries`、以及"要不要再来一轮"。

### 验收

- 灌一个"planner 说 UTC、executor 说 HKT"的构造用例：**两个值都被丢弃**，
  实际用的是解析器的裁决结果，台账里 `source` 写明出身。
- 告警原文里既没有日期也没有时区时：**零次生产调用**，用户看到**两个分开的问题**，
  不是一句合并的"时间信息不足"。
- ask 模式这条链路本来就是对的，**别动它**；现有 39 条 `mode=ask` 逐条不变。

## 2. 第二个缺陷 —— 闸门拒绝没有分类

这次真正让人看不懂的不是闸门拦了，是**拦了之后用户不知道发生了什么**。

拒绝至少有三种，**处理方式完全不同，现在很可能落在同一个桶里**：

| 拒绝原因 | 该怎么呈现 | 绝对不能 |
| --- | --- | --- |
| **用户没给**（缺日期 / 缺时区） | 一句话问用户，放在答案最显眼处 | 说成"没有异常" |
| 🔴 **我们内部不一致**（本次） | 说成**我们这边的接线缺陷**，落 telemetry，**不要去问用户** | 伪装成 gap 让用户来补 —— 用户补不了 |
| **配置故意限制 / 对面拒绝**（`scope_refusal` 那类） | 说成"这是配置里的**故意限制**，不是空日志、不是缺映射" | 说成"查不到" |

外网快照里 `scope_refusal()` 的 docstring 已经写死了第三类和第一类的区别
（「查不出 app 名」和「被人为划出范围」是两回事，两者都产生零候选）。
**本次要补的是第二类：一个因为"我们自己两个组件对不上"而产生的拒绝，是 bug，不是 gap。**

这条直接对应六期计划 §4 的四段渲染契约：**为什么停在这里 / 谁能解开**这一段里，
`who_can_close` 在这三种情况下分别是**用户 / 我们 / 配置的拥有者**，不能都写成"用户"。

### 验收

- 构造三个用例（缺时区 / 内部不一致 / repo 超范围），
  三段渲染里的 `cause` 和 `who_can_close` **三条各不相同**；
- 内部不一致那条**不出现在给用户的提问里**，但在台账和 telemetry 里可定位到**具体是哪个字段**。

## 3. 一般规则：**模型只做选择，不写工具参数**

第 1 节是这条规则的一个实例，值得单独立起来，因为它挡住的是一整类还没发生的事故。

- **选什么**（走不走 incident、下一轮换哪个关键词、要不要再来一轮）→ 模型；
- **参数长什么样**（时刻格式、时区、app 名、文件名、alarm 名）→ 确定性代码从单一来源产出。

理由是外网五轮返工的总结：**每一次缺陷都是"我们对他们环境里的某样东西下了断言"** ——
名字（`hk1` / `hkl`）→ 响应形状（JSON 当文本读）→ 值格式（`2026-07-30 03:15 HKT` 原样传被拒）。
**让模型自由生成参数，等于把这条断言从代码里挪进每一次推理，还没法写测试。**

## 4. specialist 协作 —— 这条也是真的，但排在上面两条后面

### 现状（外网快照实测）

`webapp/incident_investigator.py` 里**一行模型调用都没有**。它是纯确定性管道：
解析告警 → 代码图推关键词 → 最多 6 次 MCP → 脱敏聚合 → 返回。
**它不是 agent，它是一个会 streaming 报进度的检索函数。**
所谓"多轮"，全靠主 agent 看着回包决定要不要再调一次。

### 问题的准确形状

不是"它看不到聊天记录"，是：**能看见日志的没有决策权，有决策权的看不见日志。**

具体案例：

1. 第一轮关键词由代码图推出（`SmsDeliveryJob`、`TimeoutException` 这类），真机回来 200 行；
2. 隔离区把它压成：异常类计数（前 6 类）+ **前 5 行、每行 300 字**的脱敏摘录
   （`_MAX_EXCERPTS=5`、`_MAX_EXCERPT_CHARS=300`）；
3. 主 agent 拿这个包决定要不要换关键词再查 ——
   **可是"该换成什么"的依据（比如 190 行里反复出现的同一个下游主机名），
   恰恰在被砍掉的第 6~200 行里**；
4. 于是它只能猜着换，或者干脆不换，直接下结论。

> 外网之前的 spec 里写过「明确不做 multi-agent」。那句话**挡的是按领域拆**（代码 agent / 数据 agent），
> 那个理由仍然成立。**按"决策要贴着数据"拆是另一回事** —— 这一条外网改口，理由就是上面这四步。

### 要加的是三条**有类型**的线，加一根已经存在的总线

| 线 | 内容 | 现状 |
| --- | --- | --- |
| **① 下行 task brief** | 这个任务要闭合用户的哪个问题 / 本轮已确认的事实（含第 1 节那条 window fact）/ 本轮已经试过什么（关键词、source、窗口）/ 剩余预算 | 完全没有，全靠主模型重新打一遍参数 |
| **② specialist 内循环** | 在隔离区里看全量行、自己决定再查一次。**上界写死**：最多 K 轮 / Q 次查询 / S 秒，且**每轮必须换掉一样东西**，否则停 | 没有 |
| **③ 上行 handoff** | 业主已拍板的四段（做了什么 / 拿到什么 / 为什么停 / 谁能解开）+ **一条带理由的下一步建议**（「证据 e7 出现 `FooClient`，建议查仓库 X 的代码」） | 只有结果包 |
| **④ 横向台账** | 主循环和 specialist 写**同一本只追加的台账**（证据 id / 尝试过什么 / gap 及原因），派活前先读 | **就是 P0 那本，已经落盘了** |

**④ 值得单独强调**：你们要的"共享 memory"，物理载体就是 P0 台账，不用另造一套。
共享的是**结论、尝试和出身**，不是对话文本。

🔴 **② 的硬约束和第 3 节同一条**：specialist 内部的模型**只从候选动作里挑**，
候选仍由确定性的 plan 生成器产出。**不要把 MCP client 交给模型。**
这次的时区事故就是"让模型写参数"的直接证据 —— 在内循环里放开，它会以每轮一次的频率重演。

### 脱敏闸门：不动，只挪一刀

specialist 变成 LLM ≠ 把原始生产日志给模型。

- **PII 闸门一步不动**（手机号、邮箱、id 照旧指纹化；出口按值整包指纹化那层也不动）；
- 移动的只有**"聚合成 5 行"这一刀的位置**：从「进模型之前」挪到「进主上下文之前」；
- specialist 看到的是**脱敏但完整**的行；主上下文、session、浏览器看到的仍是聚合分类。

⚠️ **有一件事是业主的决定，不是外网能定的：内网的模型（sol / terra）到底允不允许处理生产日志正文。**
这条不定，② 不要开工；① ③ ④ 不受影响，可以先做。

## 5. 不要现在加第二个 specialist

挑 specialist 的标准是**有没有一条真实边界**，不是"这个领域看起来该分开"。按这个标准过一遍：

- **代码定位 specialist** —— 看着最该有，因为实测 `read_file` 返回**裸字符串**、
  `search_code` 返回**裸行列表**，唯二能产出可核引用的工具返回的都是非结构化文本，引用校验直接全拒。
  **但这是工具返回形状的问题 —— 修工具返回 `{path, line, lines}` 比加一个 agent 便宜一个数量级。
  修工具，别加 agent。**（这本来就是 P2 的一部分。顺带：引用后缀白名单漏了 `.js` / `.groovy`。）
- **业务数据（UAT CSV / 表述信息）specialist** —— 边界弱，现在不值。

结论：**把一个 specialist 做透，外加一张能容纳第二个的注册表**（第二个的成本是加一条配置，不是重写调度）。
三个 specialist 各自空转、答案对不上号，比现在这个"奇怪"难查十倍。

## 6. 顺序

```
第 1 节（时区单一来源）        ← 最小、最急、这一轮的直接病因，独立提交
第 2 节（拒绝分三类）          ← 挂在已有的四段渲染契约上
P1 / P2（Answer Gate、引用降级）← 六期计划原样，上一轮实测确认的缺陷区
第 4 节 ①③④（brief / handoff / 台账当总线）
第 4 节 ②（specialist 内循环） ← 需要业主先答"模型能不能读生产日志正文"
```

**② 不能提前**：内循环一开，一次告警会打出 3~5 倍的生产查询（打的是同事的服务器），
而在 ①③④ 的账目建立之前，**没有任何办法判断多出来的那几轮有没有让答案变好**。

## 7. 请先回报的四件事（不阻塞第 1 节动工）

**原样回传，不要总结、不要改写**；不要贴原始日志 / 未脱敏 payload / 真实 alarm name，
需要举例时用占位符或工具自己给的指纹。

1. **那个 scope gate 的真实名字和契约是什么？**（模块名 + 它比较的是哪些字段 + 拒绝码取值）
   外网只从口头回报知道它存在，不知道它的形状。
2. **这次到底是哪一种？**
   ① 两个模型都在猜（告警原文里根本没有时区）；
   ② 告警原文里有，planner 读对了，executor 丢了或改了；
   ③ 两个模型读到的输入本来就不一样。
   —— 三种的修法都被第 1 节覆盖，但**诊断不同，telemetry 该记的东西也不同**。
3. **告警原文里到底有没有时区**（有 / 没有，一个字就够）。
4. **`webapp_data/agent_turns/` 这一轮的记录，能不能定位到"具体是哪个字段不一致"？**
   能 → P0 的逐条 telemetry 达标；不能 → 补上，这是第 2 节验收的前提。

## 9. 一句话对外说法

> 这次不是"没去查"，是**派了活、活被我们自己的闸门拦下来** ——
> 因为**同一个时区，规划和执行各说了一遍，说的还不一样**。
> 闸门拦得对；坏的是让两个模型对同一个事实各表述一次，
> 以及**拦下来之后没变成一句能问用户的话**。
> 修法：这类"猜错了会静默给出自信错答案"的参数，一律由代码从单一来源解析，模型只做选择、不写参数；
> 拒绝分成"用户没给 / 我们内部不一致 / 配置故意限制"三类，各说各的话。
