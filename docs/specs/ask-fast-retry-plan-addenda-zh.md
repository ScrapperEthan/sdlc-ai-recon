### 1.1（#1）你们的确定性 syntax signature 比我的方案对

我提"随机签名或不生成签名"，是只盯着"别把恢复挡住"，**没想过它同时把"同一个坏输出不该重复执行"这条保护一起拆了**。

`tool + SHA-256(raw arguments)` 是正解，而且它同时满足两个方向：

- **同一个坏 JSON 再来一次** → 同签名 → 挡住（应该挡）
- **不同的坏 JSON / 改好的 JSON** → 新签名 → 放行（应该放行）

**我的方案只做到第二个方向。采用你们的。**

### 1.2（#2）我把一个条件性机制写成了绝对结论

你们是对的：如果模型下一轮给出**合法且不同**的参数，签名会变，不会命中 `{}`。
所以那不是"任何坏 JSON 都永久无法恢复"。

**而且还有一层，你们列在理由第 3 条里，值得写进 implementation MD**：

> **当前 Fast 根本没有第二个带 schema 的工具轮。**

所以这个 dedupe 风险在**现在的代码里根本不会发生** ——
它是**我们加了 repair 轮之后才会出现的未来风险**，而 #1 的 syntax signature 正好在它出现之前堵住。

🔴 **请把这个先后关系写清楚**，否则读者会以为在修一个现存 bug，进而去做不必要的分支重构。
缺陷的正确名字就用你们给的：**"错误归因 ＋ 重复恢复受阻"**，按 parser / repair budget / deterministic syntax dedupe 三部分分别修。

### 1.3（#3）三个量必须分开，这条是正确性问题不是措辞问题

`proposal_attempts` / `dispatch_attempts` / `repair_rounds` 三个量分开，同意。

**理由要写进 MD**：syntax failure 说成"工具试了 1 次"，用户会以为**工具或对端已经执行过了**。
在事故场景里，"我们已经查过 Portal 了"和"我们连请求都没发出去"是完全不同的结论。

这和这个项目已经反复出现的那条规矩是同一条：
**「提议过」≠「执行过」，正如「不知道」≠「没有发生」。**

文案用你们的：**"调用参数未通过语法校验，工具未实际执行"**。

### 1.4（#4）你们抓到一个我完全没想到的安全问题

`unresolved_reference` 独立成类、默认不 repair —— **接受，而且这条比我的方案重要得多。**

你们列的三个后果里，**第三个我完全没想到**：

> 泄露或枚举系统性的候选集合。

让模型"猜另一个 repo id"，等于给了它一个**枚举合法标识符的探针**。这是安全边界问题，不是分类问题。

第二个后果也要单独记：

> 把"目标不存在于当前 snapshot"误写成"参数格式错误"。

🔴 **这和 `0% = 双厂商备用，不是关掉了` 是同一个形状** ——
一个**系统事实**（这个 id 不在镜像里）被重新渲染成**另一类事实**（你写错了）。
这个项目已经在这个形状上栽过三次。你们这次提前拦住了。

**另外这条要照做**：`list_repos.group` 那种**静态公开集合应该进 schema enum**。
schema 能证明的才归 `bad_arguments` —— 这个判据干净、可测。

补一条硬化建议：`safe_for_model=true` 这个标记**必须由工具自己的代码设置**，
不能来自配置、更不能来自模型可影响的任何输入。

### 1.5（#5、#7）我自相矛盾了

我在 PLAN 里写：**"只有'模型改了下一次输出就可能成功'的失败才值得再花一轮"**，
然后**在下一段就把 `internal_error` 放进了可重试集合**。

你们用我自己的原则驳回，**驳得对**。内部异常不满足那条原则；自动重放还可能重复成本或撞上未来的非幂等行为。

**repairable 集合本轮固定为 `{bad_call_syntax, bad_arguments}`。**
你们那条准入规矩也接受：**新增任何 repairable class，必须同时给出确定性分类器、模型安全反馈和回归测试。**

### 1.6（#6）我的"保守"其实是污染

我以为"未迁移的一律落 `internal_error`"是保守选择。**错了** ——
把 data unavailable、not found、refused、业务校验失败全部说成"系统 bug"，
**污染 telemetry，也污染给用户的行动建议**。

`unclassified_tool_failure` 是诚实的桶。而且它正是这个项目那条规矩用在错误分类上：

> **「我们还没分类它」≠「这是我们的 bug」。**

### 1.9（#9）我自相矛盾，而且这条是结构性的

这正是我一路在你们文档里挑的那种毛病，这次出现在我自己的文档里。**接受你们的替代方案。**

> 强行追平轮数会把 Fast 重新做成 deep，并把配置时的静态上界误当作质量指标。

**对。轮数是代理指标，而这个代理指标和设计意图冲突。能力对等应该用结果衡量，不是数轮数。**

（我仍然要保住"每次提交都有便宜的自动守卫"这件事 —— 但那要用**机制断言**，不是轮数。见 §2.4。）

### 1.19（#19）这条我要单独认

我把业主说的**"经常"**，写成了 PLAN 里的**"业主每天撞到"**。

**把一句未量化的用户描述，写成了统计事实。**

## 2. 六条补充 —— 这些是修正**创造出来的**新缺口

### 2.1 🔴🔴 最重要的一条：迁移顺序现在决定 P1 的成败

`unresolved_reference`（#4）、`unclassified_tool_failure`（#6）、`internal_error`（#5）全部不可 repair 之后，
**repairable 集合只剩「schema 可证明的参数错误」。**

于是：

> **P1 的实际价值，完全取决于哪些工具先迁移到结构化错误。**

具体风险：截图一那次失败的原句是 **「当前文档查询参数不兼容」**（`mdc_knowledge`）。

- 如果它落 `bad_arguments` → P1 上线，业主那个症状**被修好**；
- 如果它落 `unclassified_tool_failure` → P1 上线，业主那个症状**一点没变**，
  因为它根本不进 repair 循环。

**所以请在 implementation MD 里先回答一个问题：**

> 🔴 **`mdc_knowledge` 那句「参数不兼容」，在新分类表里落哪一类？**

- 落 `bad_arguments` → **它必须在第一批迁移名单里**（这是 P1 见效的前提）；
- 落别的类 → **要么扩大第一批迁移范围，要么现在就把"P1 不解决截图一那个症状"这件事说清楚**，
  不要等上线后业主发现症状还在。

**这一条不是异议，是你们的修正让它从"无所谓"变成了"决定成败"。**

### 2.2 ⚠️ 截图二那个"指错门"的 bug，本轮其实修得到 —— 请把它留在验收里

#13、#16 把 Agent terminal 和 `invalid_proposal` 移出本轮，**这个范围外网接受**。

但请注意：截图二那个最伤人的 bug ——

```
屏幕说：Harness 未批准进入 Incident runtime   → 用户去查权限/审批
真相是：Portal MCP connection_refused         → 对端/网络问题
```

—— **它不是 terminal 类型问题，是 ledger ＋ projection 问题。**
它的成因是"读了另一份记录"＋"missing 被压成 `false`/`0`"。

**所以它被 #10（typed execution ledger）和 #11（字段三分类）覆盖，本轮就能修好。**

🔴 **请把这条端到端断言留在本轮验收里：**

> 一次 **runtime 已进入、MCP 对端失败** 的 run，
> 面板归因指向**对端**，**不出现"Harness 未批准"**。

这条直接回应业主"Agent 也要顺带修"的要求 —— 而且是那部分里最值钱的一条。

### 2.3 repair budget 的 resolved 值要落进 ledger

#9 定了"repair 上限等于 resolved config，不在 CI 硬编码"。同意。

**那就必须把 resolved 值写进 terminal ledger**，否则 release gate 拿到一个结果时，
**无法知道那次跑的是什么配置** —— 一个 3/39 和一个 30/39 的差异，可能只是有人改了环境变量。

这是 #10 那个 typed ledger 的自然字段，不是额外工作。

同理建议一起落的：resolved 的 `MAX_TOOL_ITERS`、`FAST_MAX_REPLANS`、repair 上限。
**"这次跑的是什么配置"必须和"这次跑出什么结果"存在同一条记录里。**

### 2.4 release gate 要阻塞，机制断言要进普通 CI

#17 的拆分接受（普通 CI = mock/unit/contract；release/UAT = 39 × 2 模式 × 3 次）。两条补充：

1. 🔴 **release/UAT 那道 gate 必须是阻塞发布的，不是 advisory。**
   这次退化能一路走到业主面前，根因就是"不能比原来差"**没有任何自动守卫**。
   换成一道没人拦的建议，等于换了个地方重犯。
2. **#9 替代方案里那五条机制断言，进普通 CI。** 它们便宜、确定、不碰 provider：
   - 成功后立即锁 schema；
   - 仅 repairable failure 且额度未尽时才出现后续带 schema 的轮；
   - repair 上限等于 resolved config；
   - 失败链只进入下一次修复输入；
   - 同 `(tool, args)` 不会第二次 dispatch。

   **这样"每次提交都有守卫"和"不把 234 次真实模型调用塞进 CI"两件事可以同时成立。**

### 2.5 #21 有一个后果，必须写下来

"repair 轮只暴露 open repair chain 对应工具的 schema" —— **接受，而且比我的设计好**，
它挡住了"借修参数之名扩大调查范围"。

但它有一个用户可见的后果，**请明确写进 MD，不要让它以后变成一个"意外"**：

> 🔴 **在 Fast 模式下，「我调错工具了」是不可恢复的；只有「我参数写错了」可恢复。**

因为"换一个工具"属于**重新规划**（replan），而 Fast 的 `FAST_MAX_REPLANS=0` 是有意的产品定位。

**这是一个正确的边界选择，但它是一个边界。**
写下来，这样以后有人报"它为什么不换个工具试试"的时候，答案是设计，不是 bug。

### 2.6 一条小的：#4 的 `safe_for_model` 标记要有归属

见 §1.4 末尾：该标记**必须由工具自己的代码设置**，不能来自配置或任何模型可影响的输入。
一句话的事，但它决定了 #4 那道闸门是真闸门还是纸闸门。
