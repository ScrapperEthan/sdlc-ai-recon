# RUNBOOK-75 实测结论 —— 业主那句"基本上",在真实数据上不成立

> 内网 2026-08-05 拉了 `53238bb`,在真实 UAT 快照上跑完 RUNBOOK-75。
> 本页只有**聚合计数**,没有数据行、没有人名、没有仓库清单。
>
> **一句话:** 三条实现基本正确,发现我一个 runbook 脚本缺陷(已修),
> 以及**两个必须问业主的问题**。

## 一、最重要的一条:"基本上"不是"基本上"

业主 2026-08-05 说:*"vendor 是空**基本上**也是因为 percentage 为 0"*。

实测(用修正后的三表连接):

| 结果 | 行数 |
| --- | ---: |
| 匹配上的子行 | 2,967 |
| 其中 vendor 为空 | 1,339 |
| ✅ 解释成立(0% 路由) | **283** |
| 🔴 **解释不成立(有真实流量、无厂商记录)** | **244** |
| ⚪ 无法判定(百分比读不出来) | 812 |

**在能判定的 527 行里,解释只成立 53.7%。** 这不是"基本上",这是"一半一半"。

### 这件事为什么重要

如果我当初把业主那句话**实现成规则**(空 vendor → 判定为 0% 路由),这 **244 行会从视野里
彻底消失** —— 而它们恰恰是唯一需要人看的那批:**有真实流量在跑,却没有权威厂商记录**。

这是前四轮教训的第五次验证:**别把对方的概括写成规则,写成可核对的检查。**
逐行复核这个决定,是被真实数据证明的,不是风格偏好。

### 但要克制:244 ≠ 244 个缺陷

内网明确提醒了(我认同):解释不成立**有两种可能**,而我们分不出来 ——

1. 真实的数据缺口:这条路由确实没登记厂商;
2. 四张表**导出时刻不同**造成的错配(`mixed_export_times`,老问题)。

**无论哪一种,都不构成"可以推断出厂商"的理由。** 这句话已经写进 `vendor_verification`
的输出里,跟着数字一起走。

### 顺带:渠道槽位

| live | idle (0%) | unknown |
| ---: | ---: | ---: |
| 1,941 | 37 | 1,880 |

`idle` 只有 37 —— 也就是"以前算活跃、现在不算"的量很小。但 `unknown` 有 1,880,
说明 `traffic_percentage` 这一列本身的缺失率很高,**这是另一个独立的数据质量问题**。

## 二、我的缺陷:RUNBOOK-75 任务 C 的脚本

`router_for_rule()` 按 `business_category + channel + route + router` 四列连接,而
`business_category` 通常来自 `tbl_use_case`(除非子表自己带)。**我写的验证脚本初始化了
`m = None` 却从来没填充它**,于是每一行都传了空的 master category 进去。

`_key_of()` 遇到任何一列为空就拒绝匹配 —— 这是**正确**的行为(部分键匹配会连到别人家的厂商),
所以脚本报了 **0 matched**。

| 方法 | 匹配到的子行 |
| --- | ---: |
| RUNBOOK-75 原脚本 | **0** |
| 修正后的三表连接 | **2,967** |

**引擎的连接实现一直是对的**(`impact_report.py:552` 正确地传了 master),错的只有验证脚本。

**已做:**
1. 修正了 runbook 里的脚本(建 `use_case_id → business_category` 映射)+ 加了健全性检查
   ("如果 matched 是 0,先怀疑脚本")。
2. 加了 `ThreeTableJoinTest` 合成回归测试:证明**没有自带 category 的子行,只有在提供 master
   category 时才能匹配**,以及**绝不能靠丢掉空列来"修好"匹配**。
3. 按内网要求,**没有**把上面任何聚合数字写进测试 —— 它们是快照特定的,下次导出就会变。

## 三、`send_mode`:绑上了,但字典是不完整的

乐观绑定成功了,这一列**真的存在**。但取值分布打脸了字典:

| code | 行数 | 字典定义 |
| ---: | ---: | --- |
| 3 | 1,435 | send by single channel |
| **0** | **903** | 🔴 **没有定义 —— 而且是第二多的值** |
| 2 | 249 | send by priority |
| 1 | 148 | send at the same time |
| **5** | **72** | 🔴 **没有定义** |
| **4** | **3** | 🔴 **没有定义** |

**约 978 行(≈35%)带着一个谁都没定义的编号。**

已做:未定义编号**保持未定义**(不猜),并且**从交叉验证里排除**(不理解的比较比不比较更糟)。
但光排除会让这 978 行**不留任何痕迹** —— 所以新增了 `undefined_send_mode` 数据质量发现,
把编号和行数报出来。

交叉验证在真实数据上产生 **30 条** `send_mode` / `rule_text` 分歧。现行策略(rule_text 权威 +
如实报告分歧)内网确认是安全的,**保持不变**。

## 四、`>` fallback 语义:真实数据验证通过

```
stage_transition: fallback_on_failure
stages_are_live: False
```

2,640 条可解析的 `rule_text` 里,**418 条含 fallback 阶段**。

也就是说 **418 条用例的影响面口径发生了实质变化** —— 以前会把表达式里所有渠道都算成活跃流量,
现在只算第一阶段。内网确认报告措辞正确,**无需进一步改动**。

## 五、词典:实现有效,但我的指标是废的

占位符抑制**按预期工作**。内网填了排名前 20 的 token 并存成 UTF-8:

| 状态 | 填之前 | 填之后 |
| --- | ---: | ---: |
| filled | 23 | 43 |
| placeholder | 235 | 215 |
| missing | 4 | 4 |

**但 `repos_with_any_meaning` 纹丝不动:459/460 → 459/460。**

我选错了头号指标。几乎每个仓库名都含至少一个常见 token,所以"至少解出一个"**在开工之前就已经
饱和**。如果拿它汇报,内网填了一整天会显示成"零进展"。

**已修:** 报告改为以两个真正会动的指标为准 ——

- `token_slots_decoded / token_slots`:所有名字里所有 token 的**解出率**
- `repos_fully_decoded`:**整个名字没有一处未解释**的仓库数(读的人真正感觉到的那个)

`repos_with_any_meaning` 保留但明确标注"**不要读作进展**"(它下降仍然有意义)。

## 六、⭐ 2026-08-05 更新:两个问题都答了,而且答案纠正了我一个危险的实现

### 问题 A(244 行)—— 业主决定:**不报成数据质量异常**

理由在 `docs/ROUTER-SELECTION-RULES-zh.md`:整族 router 是**刻意跳过**的
(`would NOT choose ICCM related router`、`can ignore ... HUTCHISON_GW related router`),
而且有些渠道的厂商**根本不由这一列决定**(PUSH 看 app name,SMS 看 telecom/delivery mode)。

**所以"有流量但 vendor 空"是预期形状。** 已改成:只报计数,无严重级,措辞里删掉 "unexplained"。
唯一保留的禁止项不变:**空 vendor 永远不构成"可以推断出是哪家"的证据。**

### 问题 B(`send_mode` 0/4/5)—— 完整字典页到手,4 和 5 解决了

| code | 含义 | 说明 |
| ---: | --- | --- |
| 4 | Send by separately | 第一份节选被截断了,所以看起来"没定义" |
| 5 | **Mixed mode** | ⭐ 正是 `rule_text` 的 MIXED —— **交叉验证第一次能正面比对混合表达式** |
| **0** | 🔴 **仍然不知道** | 903 行。记为**已知的未知**,不是漂移 |

`send_mode` 的三态处理已实现:`known`(1–5)/ `pending`(0,legitimate 但读不懂)/
`unexpected`(真漂移)。**0 报 info 不报 warning** —— 一个 903 行都在用的值,叫它"数据契约漂移"
是过度指控。

**代码 4 故意不给 `rule_text_equivalent`**:表达式语法里没有"separately"这个操作符,
硬映射到最像的那个,会凭空制造出一致或不一致。

### 🔴 但最重要的是:这批资料推翻了我对 `traffic_percentage = 0` 的实现

> `if message is high-risk, choose dual vendor with HTCL and CSL,`
> **`primary 100% HTCL & 0% for CSL`**

**0% 是「双厂商的备用方」,不是"关掉了"。** CSL 挂着 0%,正是 HTCL 挂掉时接管的那一家。

我上一轮把 0% 写成 "must not be counted as live" —— 问"HTCL 挂了谁接管",
**我会把唯一的答案删掉**。这比多算更糟。

已修正:0% 的语义改为「已配置、当前不承载流量」,三种可能(双厂商备用 / 已登记未就绪 /
真停用)**无法从这一列区分**;新增 `standby` 和 `has_standby` 两个字段;报告措辞改成
**故障问题必须包含 0% 渠道**。详见 `docs/ROUTER-SELECTION-RULES-zh.md`。

> 这和 `>` fallback 是**同一个形状**:平时不发、故障时正是它接管。同一个原则第二次出现。

## 七(历史)、当时提出的两个问题原文

这两条**我不能替业主决定**,而且都会改变引擎的默认行为。

### 问题 A —— 那 244 行(有流量、无厂商)要不要默认报成数据质量异常?

- **选项 1:默认报。** 好处是暴露得早;风险是如果大部分其实是"导出时刻不同"造成的,
  就会有一大批噪音,重蹈 RUNBOOK-53 那次 439/499 噪音的覆辙。
- **选项 2:等四张表同时刻导出之后再报。** 好处是干净;代价是要等 DBA 那张工单。

**我的建议:选项 2,但现在就把数字显示出来。** 已经这么实现了 —— `vendor_verification`
把三个数字放进报告摘要,但**不**升级成 exception。等同时刻快照到手,再决定要不要升级。

### 问题 B —— `send_mode` 的 0、4、5 是什么意思?

尤其是 **0,它有 903 行**。

拿到答案后**不需要改代码**:写进 `config/business_enums.json` 的 `data_dictionary` 和
`rule_text_equivalent` 两处即可。**内网可以直接写在盒子上** ——
新增了 `config/business_enums.local.json`(gitignored、自动优先读),
所以你们不用等我推送,当天就能生效。

顺带:那 **30 条 `send_mode` / `rule_text` 分歧**,是预期的历史配置漂移,还是应该当作数据质量
异常?现在按 warning 报告并注明 rule_text 为准 —— 在答复之前这是安全的默认。

## 八、⭐ RUNBOOK-76 真机复核结果(2026-08-05)

全部通过,**并且量出了一个比我预估大 24 倍的数字**。

### ⭐ 最重要:897 条备用路径,此前完全不可见

| 项 | 实测 |
| --- | ---: |
| **dual-vendor pairs**(在发的渠道 + 背后挂着 0% 备用) | **897** |
| live with no standby(在发,没有备用) | 1,044 |
| standby-only(整条渠道都是 0%) | 37 |

上一轮我只统计了 `standby-only` 那 **37** 个,并把它们描述成"以前算活跃、现在不算"。
**真正的漏洞在 897 那一格** —— 一条正在发的渠道背后挂着 0% 的第二家厂商,渠道级结论是"在发",
所以那 897 条备用路径**在任何一层都看不到**。

也就是说:如果有人问"HTCL 挂了谁接管",修正前的系统在 **897 个渠道**上给不出答案,
而不是我原以为的 37 个。**这是这次修正的真实价值。**

## 九、协作边界(内网提的,我同意)
